# 0035 — Light-Appearance Contrast & Residual Accessible Names

## Summary

Close the accessibility conformance gaps the card wave left behind, all three of which are colour or naming decisions made in a shared layer rather than in any one card. Two are the same defect in different elements — a colour calibrated against one background and rendered against another: the `-text` companions of the domain triplet miss AA on the near-white card surface, and the domain glyph misses 3:1 on its own 20% tint. **Only the first is light-only.** The glyph half was taken for light-only when this was written and is not: measured per hue per theme by PR 5, the base step misses in dark as well — `media` under Default, and `ok`, `alert` and `media` under Liquid Glass — which is why the remedy ends up being one step in both appearances rather than a light-appearance exception. The third is the residue of the `button-name` audit: the anatomy migration gave most icon-only controls a name, and two still have none — `InputSelectCard`'s select trigger, and the switch `InputBooleanCard` renders in its own tile at `controlStyle: switch`.

The weather card's text over condition artwork is the same family and is **not** in this change: [0030](./0030-weather-forecast-legibility.md) owns it, having landed the design system's content-imagery scrim rule and the measurement obligation with it.

**Spec:** [design-system](../specs/design-system/index.md) → [domain color discipline](../specs/design-system/index.md#domain-color-discipline) · **Status:** complete · **Depends on:** —

Supersedes issues [#191](https://github.com/fx/liebe/issues/191), [#197](https://github.com/fx/liebe/issues/197) and [#210](https://github.com/fx/liebe/issues/210). [#215](https://github.com/fx/liebe/issues/215) was folded here first and moved to [0030](./0030-weather-forecast-legibility.md) on rebase — that change already owns the scrim rule and the text treatment, so keeping a second task for it would have been the duplication this grouping exists to avoid.

## Motivation

The design system states a contrast floor and the token layer does not meet it. That is a worse failure than a card getting a colour wrong, because every card inherits it and no card can fix it: the anatomy correctly routes all colour through the triplet rather than hardcoding, so the only place the value can change is where it is chosen.

The measured figures, all light appearance:

| Element                      | Token                               | Measured | Required |
| ---------------------------- | ----------------------------------- | -------- | -------- |
| state line (small text)      | `--liebe-c-light-text` → `amber-11` | 4.497:1  | 4.5:1    |
| state line (small text)      | `--liebe-c-heat-text` → `orange-11` | 4.398:1  | 4.5:1    |
| state line (small text)      | `--liebe-c-vacuum-text` → `teal-11` | 4.450:1  | 4.5:1    |
| domain glyph on its 20% tint | `--liebe-c-light` → `amber-9`       | 1.40:1   | 3:1      |
| domain glyph on its 20% tint | `--liebe-c-ok` → `green-9`          | 2.50:1   | 3:1      |

What settles these as system defects rather than theme choices: the glyph figures sit within noise of each other across two visually unrelated themes (Default 1.40 vs. Liquid Glass 1.24), because step 9 on a 20% tint of step 9 over a near-white card cannot reach 3:1 whatever the hue. No theme choice fixes it while the pattern stands.

Liquid Glass is the useful counter-example for the `-text` half: it pins `-text` to step 12 and consequently has no violation at all (11.37:1 against Default's 4.50:1), which is direct evidence that repinning solves that half.

The accessible-name half has largely resolved itself. The anatomy's `Pill` requires a `label` and moves it to `aria-label` when the pill renders icon-only, so the HVAC mode row is now named; `ClimateSetpointControls`, `CoverCard`'s tilt row, `InputNumberCard`, `InputTextCard` and `InputDateTimeCard` all carry explicit labels. What remains is `InputSelectCard`'s select trigger, which carries no `aria-label` anywhere in the file, and the switch `InputBooleanCard` renders in its **own tile** — the `controlStyle: switch` control slot, at non-`glance` tiers. Note which switch that is: `InputBooleanDetailControls` names its switch correctly, so the unnamed one is the card's inline control rather than the dialog's.

## Requirements

### Testing Requirements

Per [architecture — Testing & Quality Conventions](../specs/architecture/index.md#testing--quality-conventions):

- `npm test`, `npm run lint`, `npm run typecheck` MUST pass; `codecov/patch` 100%; `codecov/project` no regress.
- The token contract test (`src/theme/__tests__/tokens.test.ts`) asserts every companion derives from its base. A repin changes what that test asserts, so it MUST be updated in the same PR rather than relaxed — a derivation rule loosened to accommodate a fix is the rule failing, not the fix.
- Contrast MUST be verified by **measurement, not computation** wherever the colour composites: a 20% tint over a card surface cannot be evaluated from token values, because the figure depends on what it composites onto. Decode rendered pixels.
- The workshop's a11y addon MUST report zero `button-name` and zero `color-contrast` violations for the affected stories in **both** appearances ([storybook — accessibility & interaction checks](../specs/storybook/index.md#accessibility--interaction-checks)).
- Automated contrast checking does **not** work under a theme with non-flat surfaces — axe reports `color-contrast` as incomplete ×31 under Liquid Glass ("background gradient"). A PR MUST NOT treat a clean axe run under that theme as coverage; pixel measurement is the only method that works there.
- **Let the transitions finish before reading anything, and treat a run that did not as void.** The anatomy gives every tinted part a **280 ms** colour transition (design system, "Active-state pattern"), so a reading taken sooner samples a colour the card holds in _neither_ state. Concretely, on PR 4: sampling 150 ms after render put the person avatar's initials at a mid-transition value that **cleared** 4.5:1, so the pass reported the defect as absent; 600 ms put them at the value that fails. Two obligations follow, and the second is the one that is easy to skip:
  - Wait past 280 ms after render, and again after any style the harness itself mutates.
  - **Assert the settling rather than assuming it.** Read the painted colour twice and require it stable, and — where the harness changed a style — require it to have _changed_ from what it was. A pass that cannot show both is void, not zero.

  This is the fourth known way to manufacture a false contrast figure here, and it is the most dangerous of the four: the ground-per-run, clip-chain and clipping-block traps all produce a false **1.00:1**, which looks alarming and gets investigated, while this one errs toward "no defect", which looks like success and gets shipped. It also makes axe counts non-comparable across runs sampled at different delays — PR 3's 71 nodes and PR 4's 51 differ mostly for this reason, not because anything drifted between them, and PR 4's own before-pass read clean on the first attempt for exactly this reason.

Skipping or weakening any rule to land the PR is a bug in the PR.

### Functional requirements

The [design system](../specs/design-system/index.md) owns the token contract, the domain triplet's derivation rule, the 20%-tint active pattern and the contrast floors — this change's acceptance criteria, not restated here. What implementing them requires of this change:

- **The `-text` repin is a spec edit, not only a value edit.** The design system currently states that the default theme pins `-text` to step 11 and that the base layer defines it as `var(--liebe-c-<name>)`. Whichever remedy is chosen changes that rule, so the spec's normative bullet and the token contract test MUST move with it.
- **Only the failing hues are in scope for a per-hue remedy.** If the fix is per-appearance rather than a blanket step-12 repin, the change MUST NOT silently darken hues that already pass — the state line's weight is part of the anatomy and pulling every domain darker is a visual change beyond the defect.
- **The glyph remedy changes the pattern, not a token.** No repin fixes it. The design system's 20%-tint active pattern MUST be amended to whatever clears 3:1 — a darker glyph step, a lighter tint, or a bounding treatment on the icon circle — and the amended rule is what the acceptance scenario measures.
- **Repoint the issue references.** `docs/specs/design-system/index.md` cites these defects in its Outstanding list, and `src/theme/themes/*.css` comments cite them by issue number. Each MUST become a reference to this change or be deleted as resolved, in the PR that resolves it.

## Design Decisions

- **Per-appearance `-text` is preferred over a blanket step-12 repin.** The surface tokens already resolve exactly this class of problem that way — light aliases different gray steps than dark — so the mechanism exists and is precedented in the same file. A blanket step 12 clears AA comfortably but darkens the state line under both appearances to fix a light-only defect, and it contradicts the "step 11 is the text step" rule rather than scoping an exception to it.
- **Accepting 4.4–4.5:1 as within tolerance is rejected.** It is a defensible engineering position and a poor one for this product: the design system states the floor as a MUST, three hues sit under it, and recording an exception makes the floor advisory for every future hue. The margin being small is an argument that the fix is cheap, not that the failure is acceptable.
- **The glyph fix is scoped to the pattern's own parameters.** Widening it into "reconsider domain colour" would pull in every card. The pattern has three knobs — glyph step, tint alpha, and whether the circle carries a border — and one of them clears 3:1 without touching what a domain hue _is_.
- **A live hue colours the surface, and the foreground it lands on is neutral — it does not get a derived shade of the hue.** The alternative considered was mixing the hue toward the foreground (`color-mix(in srgb, <hue> 35%, var(--liebe-fg))`), which keeps a tinge of the identity in the glyph and would have read well on the person avatar in particular. It was rejected on two grounds. The mix percentage is a constant that would have to hold against an **unbounded** input — any RGB a lamp can report, on any theme's card surface — so it could be sampled but never bounded, and a rule whose conformance cannot be established for the whole input space is the wrong rule to write into a contract that says MUST. And the neutral foreground is not a new invention needing that defence: `anatomy.css` already puts a pill label, a chip label and a slider readout on the neutral for the same reason, in the same composite. What the split costs is exactly one thing — the glyph no longer carries the hue — and [options/light](../specs/entity-cards/options/light.md#light-color-theming-uselightcolor) never granted it the hue to begin with.
- **The name residue is two controls, not a re-audit.** The original audit's 66 nodes were mostly closed by the anatomy migration as a side effect. This change fixes the two remaining and re-runs the audit to confirm the count is zero, rather than re-deriving the table.

  **Resolved by a fourth option none of the three anticipated: compute WCAG luminance in CSS and stop approximating.** The premise the three shared — that the rung can only approximate, so the argument is about where to put the exception — is false. `rgb(from …)` exposes the channels, `pow()` does the sRGB→linear transfer, and `clamp()` does the branching, so the rung can evaluate the same quantity `contrast-color()` evaluates. Swept against the function itself as an oracle over the eight identity hues and twelve bulb colours, it picks the **same** foreground on all twenty, and `plum` goes **4.42:1 → 4.75:1**.   **And the twenty fixtures were not enough, which `codex` review demonstrated on this PR.** The first form of the rung scaled the distance from the crossover by 100000 and clamped it into 0–255 — which reads as a binary switch and is a **ramp**: every luminance within 0.00255 below the crossover lands inside it and yields a mid grey. `codex` found `rgb(221, 5, 153)` by exhaustive search, where the rung produced channel 117 and a glyph at **1.00:1** — worse than the fixed black it replaced, on a colour none of the twenty covered. Exhaustively: the worst foreground the rung picks achieves **4.5707:1** against the **4.5826:1** that `contrast-color()` itself cannot beat, it differs from the true WCAG choice on 489 colours of 16777216, and the residual is entirely the dropped linear segment of the sRGB transfer, whose error is bounded at 8.34e-4 in luminance. Both figures clear 4.5:1, so the piecewise transfer would triple the expression to buy 0.012 of a ratio. Two of the three listed options were also measured and are worse: the classic luminance heuristic (`0.299r + 0.587g + 0.114b`) flips **four** of the twenty the wrong way, taking `rgb(255, 0, 255)` from 6.70:1 to 3.14:1; and a computed foreground supplied by the card is **not available for the person path at all** — `resolveAvatarHue` returns `var(--plum-9)`, a token reference rather than a literal, so the card has no value to compute from.

  **What the fix does not establish, stated because no gate here can.** Every browser this repository tests has `contrast-color()` — the harness is Chrome 149 — so the fallback's `@supports` block is never live in CI, locally, or in the workshop. `tests/e2e/lcars-fallback-rung.spec.ts` therefore lifts the rung's declaration block out of the **live stylesheet** through CSSOM and evaluates it directly, which pins the expression that was wrong and leaves the `@supports` gating unverified.

  **`docs/PRD.md` states no browser floor** — "Modern browsers only (Chrome, Firefox, Safari, Edge)", with no version, no `browserslist` and no Vite target — so how much either rung matters cannot be evaluated. Whoever takes this should settle that first; a progressive-enhancement decision has no meaning against an unstated baseline.

  **Corrected: a floor _is_ stated, by Vite, and the CSS ships above it.** `build.target` is unset, so Vite 7's default `'baseline-widely-available'` applies — `chrome107, edge107, firefox104, safari16` — and every production build down-levels JavaScript to it. It governs JavaScript only: `css.transformer` is unset, so nothing lowers CSS _syntax_ — production CSS is still processed and minified, and `vite/baselineCssPlugin.ts` rewrites its layer structure, but no feature is translated for an older engine — and the panel uses `@layer`, `color-mix()`, `@property` and `:has()` with no fallback. A browser at the stated floor gets JavaScript compiled for it and CSS it cannot fully parse. **Choosing the number is a product decision** — it says which browsers Liebe supports — so it is recorded rather than taken here, with the measured support figures and three options costed in [architecture — Open Questions](../specs/architecture/index.md#open-questions), and the PRD corrected to stop claiming nothing is stated. It no longer blocks this change: with the rung now exact, the only population it could have arbitrated is browsers that have **neither** `contrast-color()` nor relative colour syntax (14.10% by `caniuse-lite@1.0.30001806`), who keep today's fixed dark glyph.

- **Dark appearance, for PRs 1–3.** The four defects this change was proposed for pass in dark; nothing in those tasks changes it, and a PR among them that moves a dark-appearance figure has overreached. **PR 5 is the first exception, and it is why this bullet was first qualified:** the claim was made about the light-appearance repin and never measured per hue in dark. **PR 5 has now measured it, and the claim was false by more than the one hue that prompted the task** — the base glyph step missed on `media` under Default and on `ok`, `alert` and `media` under Liquid Glass. **PR 5 moves every dark figure on Default and Liquid Glass, not only the four that were below the floor** — the glyph step changes for all ten triplets, so a hue whose base and text steps differ moves whether it was failing or not. On Default's dark card the ten went from 6.97 / 4.48 / 7.24 / 4.17 / 3.63 / 2.80 / 4.29 / 4.41 / 4.12 / 3.69 to 7.19 / 6.61 / 5.72 / 7.01 / 6.74 / 7.08 / 7.22 / 6.99 / 6.40 / 6.74 (light → brand); every one is a visible change to the active glyph on every icon, pill and chip of that domain. That is the cost of the remedy and it is accepted rather than overlooked: a per-hue fix would leave the pattern saying two different things about what a glyph is, for the sake of six hues that pass by margins as thin as 3.63:1. **Light and LCARS are unchanged to the decoded pixel.**

  **PR 4 is the second, and it is why the bullet no longer says "PRs 1–4".** The live-hue defect was never one of the four this change was proposed for — it was measured while implementing PR 2 and added afterwards — so the claim above was never made about it, and it does not hold: a live hue on a 20% veil of itself fails in **both** appearances, because the failure is a colour composited against itself rather than a step calibrated for the wrong ground. Measured before PR 4, on Default and Liquid Glass: the bulb glyph missed 3:1 on 21 of 40 hue×theme×appearance composites, **5 of them in dark** (worst 1.49:1, a pure-blue bulb under Liquid Glass), and the avatar's initials missed 4.5:1 on all 32, **16 of them in dark** (worst 2.19:1). PR 4 moves every one of those dark figures, deliberately and with the numbers above; it is not the overreach this bullet exists to forbid, because there was no passing dark figure to move.
