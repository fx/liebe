# 0036 — Theming Contract & Cascade Gaps

## Summary

Four gaps between what the theming spec promises and what the cascade and the selector contract actually deliver, all of them the same shape: the base layer knows something a theme or a baseline rule needs, and exposes it through a name that cannot be reached. The 44px coarse-pointer touch floor no longer applies to any Radix control, because a layered rule cannot outrank an unlayered vendor stylesheet. Custom CSS does not reach portalled overlays, because the user layer is deliberately withheld from the document-level mirror and no scoped portal host exists. A theme cannot recolour a pill or chip label, so a filled active treatment is unreachable and LCARS ships a compromise. And `liebe-section-title` is named in the contract but stamped nowhere, because nothing in the markup means "the title of a section".

**Spec:** [theming](../specs/theming/index.md) → [application mechanism](../specs/theming/index.md#application-mechanism) and [stable selector contract](../specs/theming/index.md#stable-selector-contract) · **Status:** complete · **Depends on:** —

Supersedes issues [#204](https://github.com/fx/liebe/issues/204), [#206](https://github.com/fx/liebe/issues/206), [#214](https://github.com/fx/liebe/issues/214), [#218](https://github.com/fx/liebe/issues/218).

## Motivation

The touch floor is the most consequential and the least visible. `src/styles/app.css` declares it inside `@layer liebe-base`; `@radix-ui/themes/styles.css` contains no `@layer` at all, and the build wraps it into `liebe-base` too — so **both end up in one layer, where the cascade falls back to specificity**. The floor is written on bare `button` / `input` / `textarea`; Radix's `.rt-reset` declares `min-height: 0` on the same elements with a class selector and wins. With a coarse pointer emulated, a `size="3"` select trigger measures 40px, a text field 38px — and their computed `min-height` reads `0px` and `auto` respectively, the tell that the declaration is not winning at all rather than being overridden by something specific.

**The mechanism above is a correction made while implementing PR 1**, and it matters because it changes the fix. This document originally read the defect as unlayered vendor CSS outranking every layer — true of the stylesheet as it ships, and not true of the panel, because [0012](./0012-theming-engine.md) already wraps every vendored sheet at build time. Had the diagnosis been right, layering the sheet would have been the whole fix; being wrong, layering it was already done and the fix is to layer it one level _lower_.

**And "one level lower" turned out to need two moves rather than one**, which the same measurement is what caught. Demoting the vendored sheets beneath `liebe-base` left `app.css`'s universal reset above them, and `* { padding: 0; margin: 0 }` above a component sheet does to Radix precisely what it did to the card anatomy before 0010 layered it: Radix table cells lost 16px of padding and inline code 5px, across 156 of the workshop's 622 stories. A reset is written to lose, so it has to sit below what it must not touch — hence three baseline tiers, not two. Worth recording because the second defect is invisible in the measurement the first one asks for: every control it names came back at 44px with the reset regression fully present.

**Demotion is not free, and the third defect is the general form of that.** Layering a vendored sheet below the baseline does not only let a first-party rule win where it was usefully losing — it activates _every_ first-party rule that was losing to that sheet. `GridLayoutSection.css` styles the grid's drag handles as `.react-resizable-handle-s`; react-grid-layout styles the same handles as `.react-grid-item > .react-resizable-handle.react-resizable-handle-s`, one class deeper, so the vendor has always won and Liebe's version has never rendered. Demoting the package made ~150 lines of never-executed CSS live at once: the south handle went from a 28×28 rotated square to a 40×20 bar shifted 16px left and the east handle from 28×28 to 20×40, which was enough for a handle to cover a card's action button and swallow the click. Nothing before the e2e run could see it — the workshop renders no grid, and the story sweep that caught the reset regression has no resize handles in it to measure.

So the rule this change lands is **demote per package, not per `node_modules`**: a sheet goes below the baseline when something first-party needs to outrank it and the consequence has been measured. Radix Themes qualifies, because the touch floor is what needs to outrank it. **The grid packages did not when PR 1 landed, and do now** — their dead handle rules carry the same touch-target intent as the floor and had never applied, but making them live changes how the grid is operated, so it needed its own before/after evidence. That evidence is PR 5, which gathered it and demoted both.

This matters because touch is Liebe's primary input mode: `AGENTS.md` lists touch-first UI as a core design principle and the design system requires discrete controls to be ≥44px in at least one dimension. `size="3"` alone does not satisfy that rule — every measurement above is at `size="3"`. The floor was what closed the gap, and it closed it for every `Select`, `TextField`, `TextArea`, `Button`, `Switch` and dialog control in the config modals, the entity browser and the taskbar.

How it got there is worth recording, because the step that broke it was correct. The floor was unlayered until the card-anatomy work, where `app.css`'s reset had to move into `liebe-base` — an unlayered `* { padding: 0 }` was outranking every layered rule and zeroing the anatomy's padding. Moving it was necessary; this consequence was not noticed.

The portal gap is a trade-off that was taken deliberately and should not have had to be. The base and theme layers reach document-level portals, so overlays render on the active palette. The **user** layer is withheld, because user CSS selectors are the author's own and nothing scopes them to Liebe — a copy in the Home Assistant document would let a `body { display: none }` out of an imported configuration restyle the frontend around the panel. Containment beats reach, so the consequence is that a user who overrides `--liebe-card-bg` sees it on cards and not inside a dialog. The spec already names the remedy it prefers: portal into a host **inside** the shadow root, which removes the trade-off entirely because nothing is copied into the document at all.

The label gap blocks a design the design system itself describes. LCARS active parts are specified as "solid colour fills with black glyphs/labels", and only the glyph half is deliverable: `anatomy.css` pins `.liebe-pill-label` / `.liebe-chip-label` to `--liebe-muted` and `--liebe-fg`, and those are internal class names explicitly outside the contract. So a theme that fills a pill with a saturated hue cannot darken the label on it. Icon circles are unaffected because they carry no label — LCARS gives them the solid hue with a black glyph at 9.5:1, while pills and chips fell back to a 38% block of the hue with the neutral label at 6.63:1. Readable, and not the design. The same shape recurs one level down: `--part-color`, `--part-tint` and `--part-text` are internal too, so a theme wanting "this part's own hue" restates the entire ten-way `data-color` mapping the base layer already performs, as LCARS does under a private `--lcars-hue`.

`liebe-section-title` is the one gap whose right answer may be removal. It has never been stamped, and the reason is about the product rather than scheduling: a screen renders no header (its name lives in the taskbar and sidebar), and the only titled thing nearby is the `separator` grid item, which a user places anywhere — mid-grid, vertically, several per screen, or not at all. Stamping the class on a separator would promise themes a bar at the head of a section that is not what renders. An earlier revision of the spec claimed all three structural hooks shipped in 0010; that claim was false and cost a real investigation to disprove, which is the argument for not leaving a named-but-absent hook in the contract indefinitely.

## Requirements

### Testing Requirements

Per [architecture — Testing & Quality Conventions](../specs/architecture/index.md#testing--quality-conventions):

- `npm test`, `npm run lint`, `npm run typecheck` MUST pass; `codecov/patch` 100%; `codecov/project` no regress.
- The touch floor MUST be verified by **measuring a rendered control under an emulated coarse pointer**, before and after, and the evidence MUST include computed `min-height` as well as measured height — `auto` versus `44px` is what distinguishes "the rule is not winning" from "the rule is being overridden".
- Cascade-precedence changes MUST be pinned by e2e assertions against a **genuinely open overlay**, as the existing base-and-theme mirror already is ([theming spec](../specs/theming/index.md#application-mechanism)). A unit test asserting a stylesheet's text cannot observe layer precedence.
- The containment property is a security-adjacent invariant and MUST have its own negative test: a user stylesheet declaring a document-level selector MUST be shown not to affect the surrounding Home Assistant frontend.
- Theme stories MUST cover the new label token under all three built-in themes in both appearances ([storybook — story coverage](../specs/storybook/index.md#story-coverage)).

Skipping or weakening any rule to land the PR is a bug in the PR.

### Functional requirements

The [theming spec](../specs/theming/index.md) owns the layer model, the cascade order, the selector contract and the portal requirement — this change's acceptance criteria, not restated here. What implementing them requires of this change:

- **The touch floor and the portal host share a document, not a cause, and neither fix substitutes for the other.** The floor failed because Radix's stylesheet sat in `liebe-base` alongside it and outranked it on specificity; the portal fails because the user layer is withheld from the document-level mirror. **Moving overlays into the shadow root does nothing about vendor stylesheet precedence** — a portalled Radix control inside the shadow root still loses to a vendor sheet in its own layer. So both PRs are independently required and independently measured, and neither may be reported as partially resolving the other. Sequencing only: settle the layer question first (PR 1), so the portal host inherits a precedence model that already works rather than one still changing under it.
- **Moving the vendored Radix stylesheet below the baseline changes precedence for every Radix component at once.** That is the fix's cost and it MUST be measured rather than reasoned about: the same coarse-pointer probe that reproduces the defect confirms the fix, and a visual pass over the config modals, entity browser and taskbar is required before it lands.
- **The floor MUST NOT resume beating a token.** The anatomy's parts state their own sizes and reason about the floor deliberately — a pill takes `min-inline-size: 44px` to satisfy "≥44px in at least one dimension", and the 34px chip is intentional. Whatever wins over Radix MUST still lose to `--liebe-chip-height`.
- **The user layer MUST NOT be mirrored to the document _as authored_** — **restated after PR 2, because the original wording assumed an option that does not exist.** It read: if the scoped host lands, all three layers apply inside the shadow root and nothing is copied out; if it does not land, the user layer stays withheld. The in-shadow-root host cannot land (see Design Decisions), so those were never the two cases. What the requirement was protecting is containment, not the absence of a copy: a mirrored `body { display: none }` must not restyle the frontend. Mirroring the layer **rewritten** — every selector bounded to a subject inside `.liebe-portal-root`, and every at-rule that registers a document-global name dropped — satisfies that and delivers the reach. Mirroring it unrewritten remains forbidden.
- **The label token MUST default to today's behaviour.** `--liebe-muted` inactive, `--liebe-fg` active, so Default and Liquid Glass are pixel-unchanged; only a theme that fills overrides it. The internal class names stay internal — this exposes the _decision_ they encode, not the selectors **The token itself is contract, so it lands in the [token contract](../specs/design-system/index.md#token-contract) and the [selector contract](../specs/theming/index.md#stable-selector-contract) in the same PR** — a theming token whose only definition is a change document is a contract with no owner.
- **`liebe-section-title` gets a decision, not a deferral.** Either a section gains a real heading in the markup — an element that means "this section's title" because a section genuinely has one — or the hook is removed from the contract with a migration note. Leaving it named and unstamped is the one outcome this change may not produce.
- **LCARS's narrowed acceptance scenario moves with the decision.** Change [0013](./0013-built-in-themes.md)'s scenario describing a butterscotch section-title bar is currently narrowed rather than claimed; if a heading arrives, the fillet, the per-title code label and that scenario are completed here.
- **Repoint the issue references.** `docs/specs/theming/index.md` cites #206, #214 and #218 as outstanding, `src/theme/themes/lcars.css` and `src/theme/__tests__/lcars.test.ts` cite #218, `src/theme/styleInjection.ts` describes the absent `.liebe-portal-root`, and `docs/specs/design-system/index.md` cites #204. Each MUST become a reference to this change or be deleted as resolved, in the PR that resolves it.

## Design Decisions

- **Layer the vendored sheet rather than fight its specificity.** Raising the floor's specificity to beat Radix's selectors works and is specificity whack-a-mole against a sheet that changes on every upgrade. Setting explicit sizes on Liebe's own control wrappers is the most predictable and the most repetitive, and it leaves the global rule in place doing nothing — which is worse than either, because the next author reads the floor and believes it applies. Layering the vendor sheet below `liebe-base` restores the model the rest of the system already uses and makes Radix themable by the same cascade.
- **Tier the baseline internally rather than add a fourth top-level layer.** `liebe-base.reset` and `liebe-base.vendor` are sub-layers of `liebe-base`, so the three layers the [theming spec](../specs/theming/index.md#application-mechanism) makes contract stay three: a theme and a user still see one baseline that they both outrank, and the tiering inside it is not theirs to know. A `liebe-vendor` beside `liebe-base` would have been a contract change for an implementation detail, and would have put the ordering of the whole system in a name that any sheet still carrying the old statement could register in the wrong place.
- **Portal inside the shadow root, not into a scoped document container** — **falsified while implementing PR 2, and the correction reverses it.** The reasoning was sound and the option is unavailable: it is Radix's modal implementation that forbids it, not the cascade. Every Radix overlay marked `modal` (which `Dialog.Root` hardcodes and cannot be talked out of) calls `hideOthers(content)` from the `aria-hidden` package to remove everything else from the accessibility tree. That helper reconciles a target against `document.body` with `Node.contains`, which does not cross shadow boundaries, and its one accommodation — `unwrapHost` — climbs to the **first** shadow host it meets and stops. From inside the panel that host is `<liebe-panel>`, which `document.body` does not contain either, because Home Assistant nests it several shadow roots deep. The helper then logs `aria-hidden … not contained inside … Doing nothing`, keeps **no** targets, and hides every child of `document.body` — `<home-assistant>` included, and with it the panel and the very overlay that opened. Measured on the branch: `<home-assistant aria-hidden="true">` in the failure trace, and twenty e2e specs failing with `getByRole` finding no menu, no dialog and no confirm, because a role query does not match inside an `aria-hidden` subtree. This is an accessibility defect before it is a test failure: while any Liebe overlay is open, a screen reader sees nothing at all.

  The mechanism, at the line level, so nobody has to rediscover it:

  ```js
  const unwrapHost = (node) => node && (node.host || unwrapHost(node.parentNode))
  if (parent.contains(target)) {
    /* keep */
  }
  const correctedTarget = unwrapHost(target)
  if (correctedTarget && parent.contains(correctedTarget)) {
    /* keep */
  }
  ```

  `unwrapHost` returns the **first** host it reaches and stops, and that host is then tested with `document.body.contains(...)`. One shadow root directly under `document.body` therefore succeeds; two or more cannot.

  **And that is the reusable lesson, beyond this change: the workshop and every unit test put their shadow root — when they have one at all — directly under `document.body`, so they take the succeeding path. They are structurally incapable of reproducing Home Assistant's nesting.** A full green suite, both builds and 100% patch coverage said nothing about this, and only the real frontend could. Anything that depends on how deep the panel sits has to be judged in e2e.

  So the choice the spec offers is not between "strictly better" and "fallback": the preferred form is unavailable, and the `liebe-portal-root` container with all three layers mirrored at the document level — the user layer scoped by selector rewriting so nothing of it can match outside the container — is what remains.

- **The tokens move from `.radix-themes` to `.liebe-root`, and PR 2 does not work without it.** Discovered while implementing: moving an overlay inside the shadow root gets it the layers and is **not** enough to get it the tokens. Radix wraps every portal in a theme root of its own, stamped `.radix-themes` — the very selector the base sheet and all three built-in themes declared `--liebe-*` on — so each open overlay re-declared the whole contract on itself, and an element's own declaration is the value it uses however its ancestors were overridden. A user's `.liebe-root { --liebe-card-bg: … }` would have reached the dashboard and stopped at the edge of the dialog exactly as before, with the portal host in place. Declaring on `.liebe-root` instead leaves those generated roots with nothing of their own, so they inherit. It is also what the spec already said the root selector was for, and it costs the workshop's side-by-side appearance galleries one `className="liebe-root"` each — those are the only Radix theme roots outside `LiebeThemeProvider` that are meant to be token roots.
- **No z-index, and the consequence is real rather than theoretical.** The host sits inside `.liebe-root`, which Radix makes a stacking context (`position: relative; z-index: 0`), so a full-viewport overlay can no longer paint over Home Assistant's own chrome the way one portalled to `document.body` did — the same cap change [0008](./0008-camera-fullscreen-no-dom-move.md) met and answered with a temporary ancestor lift. **It lands differently on the two kinds of overlay, and the difference is what PR 6 exists for.** A Radix overlay stays modal regardless: its dismissable layer takes `pointer-events` off the document body, so HA's chrome is inert behind it and only the dimming of the sidebar is lost. `FullscreenModal` — the entity browser — has none of that machinery, so there the chrome stays clickable and the browser stops being modal. Lifting `.liebe-root`'s stacking while an overlay is open is the known remedy, and it is deliberately not taken in PR 2: it is a second standing exception to the design system's no-z-index rule, it needs the before/after a browser gives and the workshop cannot, and adding it silently inside a cascade fix is how the first exception would stop meaning anything.
- **The token contract cannot be declared on `.radix-themes`, and this is what the portal work actually turned up.** Radix stamps that class on the theme root it wraps around **every** portal — the same selector `src/styles/tokens.css` and all three built-in themes declare `--liebe-*` on. So each open overlay re-declares the whole contract on itself, and an element's own declaration is the value it uses however its ancestors were overridden. That, not the overlay's location, is why custom CSS reaches the dashboard and stops at the edge of every dialog: moving the overlay without moving the declarations would have changed nothing. Whatever container PR 2 ends up mounting therefore has to carry `liebe-root`, **and** the declarations have to move from `.radix-themes` to `.liebe-root` — which is what the spec's [Configuration & selection](../specs/theming/index.md#configuration--selection) has always said the root selector is for. The two halves ship together or not at all: with the declarations moved and overlays still in `document.body`, an overlay inherits nothing, because the document has no `.liebe-root` — a completely tokenless overlay in place of a partly-themed one. Measured on the attempt, not reasoned about.
- **Selector rewriting alone does not contain the mirror, and the gap is not a selector.** Rewriting bounds what a rule may _match_; it says nothing about a construct that reaches the frontend without matching anything. `@property --primary-color { syntax: '<length>' }` makes Home Assistant's own `--primary-color: #03a9f4` invalid at computed-value time and takes the frontend's theming with it; `@keyframes` and `@font-face` shadow a name the frontend already uses; `@page` is scoped to nothing. So the mirror carries **only** the at-rules that conditionally group other rules — `@media`, `@supports`, `@layer`, `@container`, `@scope`, `@starting-style` — and drops the rest. An allowlist rather than a blocklist, so a construct CSS ships after this is contained by default. The cost is a user `@keyframes` not animating inside an overlay, and a user `@font-face` not loading for one — the latter costing nothing, since a shadow root does not load faces declared in it either and the panel has never had them.
- **A token for the label colour, not an addition to the selector contract.** Promoting `.liebe-pill-label` to public API would freeze an internal element's structure. A `--liebe-*` custom property exposes the one decision a theme needs — what colour a label on a part takes — and leaves the anatomy free to restructure.
- **The `--part-*` internals get the same treatment or none.** Exposing the resolved per-part hue saves every scoped-rule theme from restating a ten-way mapping. It is the smaller instance of the same problem and should be decided in the same PR as the label token, since both are "the base layer knows something a theme needs".
- **A section heading is a screen/section structure question, not a theming one.** Whether screens or sections gain an optional user-set heading, and whether that supersedes the `separator` item, is a dashboard-config and grid-layout decision. This change owns the _contract_ consequence: if the answer is no, the hook is dropped.

- **The entity browser's lost modality is recorded rather than tracked, and this is where it lives now.** It was written as a task ("PR 6") conditional on PR 2 taking the inside-the-shadow-root route — the one PR 2 then established is unavailable, because `aria-hidden`'s `unwrapHost` climbs to the **first** shadow host and stops, and Home Assistant nests the panel several roots down, so every Radix modal would hide `<home-assistant>` and the overlay with it (see the Design Decision above and [theming](../specs/theming/index.md#application-mechanism)). Its own text therefore ends by saying the `liebe-portal-root` fallback retires it. An unchecked box that is not work makes the task list stop meaning "work remaining", and 0036 could never close while it sat there. It is not ticked — nobody did it — and not deleted, because the measurement is real and returns with any future attempt at an in-shadow-root portal host. Moved verbatim (change 0036 PR 5):

  > **PR 6 — The entity browser's lost modality** — _conditional on PR 2 taking the inside-the-shadow-root route, which it now cannot._ A host inside `.liebe-root` sits in a stacking context, so a full-viewport backdrop no longer paints over Home Assistant's chrome. Radix overlays would be unaffected in substance — their dismissable layer makes the chrome inert — but `FullscreenModal`, which the entity browser opens through, has no dismissable layer and no `pointer-events` guard, so HA's sidebar would stay clickable behind an open browser. The `liebe-portal-root` fallback keeps the overlay in `document.body` and so keeps today's stacking, which retires this task; it is recorded because the measurement behind it is real and would come back with any future attempt to move overlays into the shadow root.

- [x] **PR 5 — The grid's dead handle rules**: `GridLayoutSection.css` styles every resize handle one class shallower than react-grid-layout styles them, so none of it has ever rendered — including its coarse-pointer block, which asks for 32×32 and 60px-wide handles and is the same touch-target intent as the floor. Decide whether Liebe's handle geometry is the intended one; if it is, demote `react-grid-layout` / `react-resizable` into `liebe-base.vendor` and reconcile the two sets of rules (the vendor's `margin-left: -10px` and Liebe's `translateX(-50%)` currently both apply and double-shift the handle); if it is not, delete the dead rules so the next reader does not believe they are live. Either way an e2e resize before/after, because this is grid interaction and the workshop cannot see it

  **Outcome: Liebe's geometry is the intended one, because the spec already says so.** The question the task poses was answerable from the repo rather than from taste — [grid-layout](../specs/grid-layout/index.md#touch-first-sizing) states the handle geometry as a **MUST** and even carries a scenario citing the rule by line number. The requirement was never in doubt; what was wrong is that it had never rendered. The numbers live in that spec and are deliberately not repeated here. So both grid packages are demoted and the two rule sets reconciled, and deleting the rules was never really the alternative it looked like — it would have deleted a normative requirement to match an implementation that failed it.

  **What reconciliation actually took**, none of which is visible from either sheet alone:
  - **`margin: 0`** — react-resizable centres edge handles with `margin-left: -10px`, Liebe with `translateX(-50%)`. Both survive demotion, and the handle lands half its own width _plus_ ten pixels off centre. This is the shift PR 1 measured as "a 40×20 bar shifted 16px left".
  - **`transform: none`** — the vendor rotates every handle to point its grip outward. Liebe overrides that on the four edge handles because it needs the property for centring, and sets no transform on the corners, so their rotation survives and spins the `::after` dot to the wrong corner of a box whose square shape hides that anything rotated.
  - **`background-image: none`** — the vendor's grey grip SVG would sit behind Liebe's own dot.
  - **`.grid-item > *:not(.react-resizable-handle)`** — the one that was not predictable from the two stylesheets, and the reason PR 1 was right to wait. `react-grid-layout` puts the handles in the **same element** as the card, so Liebe's own "the card fills the grid item" rule matched all eight and stretched each to the full tile. Demotion made that rule win, and eight invisible full-card handles stacked over every card, the last of them swallowing every press. The grid still resized — from whichever handle was on top — so the symptom was a card that only ever changed height.
  - **A cap, which review found and measurement confirmed.** The floor is in pixels and a grid cell is not: at the 8-column breakpoint on a 480px viewport a 1×1 tile is 33×51, and eight handles at the spec's sizes covered **every** pixel — 0 of 100 sampled points free, a card that could not be dragged, tapped or opened. No handle may now exceed 40% of its tile per axis; the spec states the precedence (a free drag surface outranks the floor) and an e2e case pins it. Worth noting how it was found: `codex review` reasoned it out from the breakpoint arithmetic, and the measurement then agreed. It is the one consequence of making these rules live that neither the original task, PR 1's investigation, nor my own before/after had considered.
  - **Visible, not merely large.** `react-grid-layout` hides handles at `opacity: 0` until `:hover`, which a touch device never fires, so the floor in size alone shipped a 32×32 target nobody could see. The old attempt at this raised the `::after` dot's opacity while the vendor kept the handle _containing_ it at zero — and lived inside a `max-width: 767px` block, so it said nothing about a tablet.

  **Evidence**: `tests/e2e/grid-handle-geometry.spec.ts`, before and after on the same commit. Before, on `a35152d`: the corner handle measured **20×20** against the spec's ≥32, and the whole e2e suite was green — the defect had never been observable. After: 32×32 corners, 60×32 south, 32×60 east, visible without hover, each smaller than the card, resize still lands the tier it did before, and all 33 e2e specs pass.

  **One finding is about the test rather than the code, and it is the one worth carrying.** The first "after" run passed every assertion **while all eight handles measured the full 141×174 card** — a lower bound cannot tell `32×32` from `everything`. The upper bound that now sits beside it is what turns that green into a claim, and it was added only because `card-resize-tiers` failed independently and sent me looking. A floor without a ceiling is a measurement with one end open.

- [x] **PR 7 — Two panels in one document share the mirror**: `panel_custom` allows the production and dev panels to be registered together, and the panel deliberately resists removal, so both can be mounted in one Home Assistant document at once. The document-level mirror is keyed by slot NAME alone — `style[data-liebe="theme"]`, `style[data-liebe="user"]`, `style[data-liebe="fonts"]` — so the last panel to render wins for both, and the mirrored rules match on `.liebe-root` / `.liebe-portal-root`, which both panels' containers carry. One panel's theme and custom CSS therefore style the other's overlays. **Not introduced by PR 2** — the theme layer has had this since [0012](./0012-theming-engine.md) put the mirror in; PR 2 extends it to the user layer, and the note in `src/theme/styleInjection.ts` is where the mechanism is written down. Fixing it is an instance token on the slot **and** on the container's scope, for all three layers at once: a slot alone leaves both sheets matching both containers, and a scope alone leaves them overwriting one element. Which is why it is a task rather than a line in PR 2 — and why the two halves have to land together, the same way PR 2's own two halves did. Dev-only in practice, so it is a correctness defect rather than an urgent one

  **Outcome: per-instance keying, slot AND scope together.** Each panel mount generates a token (`useId` in `LiebeThemeProvider`, passed to `PortalHost` which stamps it as `data-liebe-instance` on the `liebe-portal-root` container). The document-level mirrors — theme (`applyThemeCssToRootOf` + `keyThemeCssToInstance`), user (`applyUserCssToRootOf` + `scopePortalCssToInstance`), fonts (`registerThemeFonts`) — carry the same token on their slots, so each panel rewrites only its own element; and the mirrored theme rules plus the rewritten user selectors are bound to the token, so each sheet matches only its own container. In-shadow-root sheets stay as authored (one panel per root). Pinned by unit tests keying two panels' mirrors to their own slots/containers and re-rendering one without touching the other, plus portal-container stamp tests.

- [x] **A theme cannot tell an identity disc from a glyph circle**: the base layer keeps the person card's initials avatar on an icon-only tile — its anchor IS the disc — by naming an internal avatar class, which a theme may not target. LCARS therefore has to except the whole `person` domain from its own icon-tile rule, so a person card falling back to the glyph circle (an `icon` override, or a name yielding no initials) keeps a solid disc on an already-tinted tile under that theme. Same shape as the gaps above: the base layer knows something a theme needs and exposes it through a name that cannot be reached. Found while implementing [0033](./0033-icon-only-cards.md)'s tile tint; either publish a contract hook for the anchor form or decide the coarse exception is the intended treatment, and pin whichever in the LCARS test and pin whichever in the LCARS test

  **Outcome: contract hook for the anchor form.** `PersonAvatar` stamps `data-avatar="initials"` on the initials identity disc (via a typed `IconCircle` prop); the internal avatar classes stay for the one base-layer background rule. LCARS narrows its icon-tile rules from the whole-`person`-domain exception to `:not([data-avatar='initials'])`, so a person card on the glyph fallback (icon override, no initials) takes the ordinary glyph-circle treatment instead of keeping a solid disc on an already-tinted tile. `data-avatar` joins the selector contract as a stamped hook with a presence guarantee; the LCARS guard pins the form-level exception and fails a `liebe-section-title`-style return of the domain exception.
