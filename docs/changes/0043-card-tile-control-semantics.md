# 0043 — Card-Tile Control Semantics & Error Recovery

## Summary

The card shell renders its tile as a role-less `<div>` carrying pointer handlers (`GridCard.tsx`), so the surface the design system calls "the primary action" is not focusable, announces itself as nothing, and has no activation route that is not a pointer. The design system's error-tile contract ([quoted under Motivation](#motivation), where it establishes the gap) depends on exactly that surface being a control, and none of its three halves exists on the shell: no button, no error-carrying dialog, and no `Retry` or `Dismiss` on it in any state. The message's only carrier today is `title={error}` on that same div — the one mechanism the contract names and forbids. Make the tile a control with keyboard and assistive-technology semantics, route pressing it in the error state to the detail dialog carrying the failure, and implement the two recovery actions.

**Spec:** [design-system](../specs/design-system/index.md) → [size-adaptive layouts](../specs/design-system/index.md#size-adaptive-layouts); [entity-cards/options/common](../specs/entity-cards/options/common.md) → [action type](../specs/entity-cards/options/common.md#action-type) and [icon-only presentation](../specs/entity-cards/options/common.md#icon-only-presentation-icononly) · **Status:** complete · **Depends on:** —

## Motivation

**What the contract says, and where.** [design-system — size-adaptive layouts](../specs/design-system/index.md#size-adaptive-layouts) states it under "Omitted from the layout is not omitted from the product":

> Concretely for a `glance` error tile: the message MUST become the tile's accessible name; the tile MUST be a button; and pressing it MUST open the detail dialog carrying the full message and the `Retry` / `Dismiss` actions. A `title` tooltip MUST NOT be that mechanism — Liebe's primary surface is a wall tablet with no hover, and `title` reaches assistive technology inconsistently even where hover exists — and `Retry` MUST NOT simply be dropped, since it is the only way out of the state.

[options/common — icon-only presentation](../specs/entity-cards/options/common.md#icon-only-presentation-icononly) binds the same rule to a second surface, under "Card states outrank suppression", requiring of an icon-only tile that "pressing the tile reaches the full message and the recovery actions".

**There are two error tiles, and neither holds the contract — for different reasons.** The distinction is the whole reason the gap survived, so it is worth stating before anything else:

- The **stand-in** error tile — what a card renders _instead of_ itself when the entity is missing or Home Assistant is disconnected — is `ErrorDisplay variant="card"` (`src/components/ui/ErrorDisplay.tsx`), reached by roughly a dozen cards. At `glance` the **component** implements the contract: a real `<button>` whose `aria-label` is `` `${title}: ${errorMessage}` ``, opening a modal that carries the full message, `Retry` and `Dismiss`. Its **callsites** do not supply the actions. Not one production callsite passes `onDismiss`, so `Dismiss` never renders anywhere; and the input-helper and weather callsites pass `onRetry` only when disconnected (`onRetry={!isConnected ? … : undefined}`), so the entity-not-found tile drops `Retry` too. So the rendered tile is a button onto a message with nothing to do about it — the button-and-dialog half held, the recovery half not.
- The **inline** error state — a card that keeps rendering itself while something it did has failed — is the shell's `data-error` tile. Every card sets it, it is stamped at `GridCard.tsx:1032`, and it holds none of the contract. This is the surface the defect is about.

Nothing in the spec distinguishes them, and `ErrorDisplay`'s component-level conformance is what makes a reader conclude the contract is implemented. Where it is implemented is on the tile that needs it least: the stand-in tile's failure is a connection the user cannot act on from the tile anyway, while the inline tile's failure is a command that just did not happen.

**And `isError` does not mean one thing.** Most cards pass `!!error` from `useServiceCall` — a service call that failed, which is the case `Retry` is obviously for. `CameraCard` passes `!!streamError` (`CameraCard/index.tsx:516`), a stream that would not start, with no command to repeat. `useServiceCall` also sets an error before dispatching at all, on a validation or capability refusal, where there is nothing in flight and nothing to retry. `PersonCard` and `BinarySensorCard` pass a literal `false`. So "the failure the tile carries" is a family of failures with one flag, and a recovery contract written for the service-call case alone would specify an impossible `Retry` for the others.

**What the inline error tile actually does.** A light whose `light.turn_on` failed renders its normal layout with `ERROR` on the state line (`LightCard/index.tsx:593`), an error outline and one pulse from the shell, and `title={error || undefined}` on the tile (`LightCard/index.tsx:671`) — the forbidden tooltip, and on a wall tablet an empty gesture. Nothing on that tile offers `Retry` or `Dismiss`: `useServiceCall` exposes `clearError` and no rendered control calls it, and the recovery actions the stand-in tile can render are on the other surface and unreachable from this one. `EntityDetailDialog` takes `entityId`, `open` and `onOpenChange` and nothing else, so even reaching the dialog reaches no message and no actions.

**And under it, the tile is not a control at all.** `GridCard.tsx:1000` opens a `<div>` with `onClick`, `onPointerDown`, `onPointerUp`, `onPointerCancel` and `onPointerLeave`, no `role`, no `tabIndex`, and `GridCard.css` declares no focus styling anywhere. So a keyboard or switch user cannot reach any card's primary action on any card at any tier, an assistive technology announces the tile as a group of text, and the error state's required button is missing because the tile was never a button in any state. The error contract is the part of this that a spec already pins; the operability underneath it is the part that makes the error contract impossible to satisfy locally.

**`iconOnly` makes it more visible without causing it.** Change [0033](./0033-icon-only-cards.md) PR 1 shipped the half that was its own — the shell resolves an accessible name from the entity and substitutes the failure message for the state when `isError` holds (`GridCard.tsx:747–756`) — which is `common.md`'s "the message becomes the tile's accessible name", and only for icon-only tiles. The rest of that sentence, "and pressing the tile reaches the full message and the recovery actions", it left alone. Suppression removes the embedded controls that were the only keyboard-reachable targets on such a tile, so an icon-only card in an error state is a tile a keyboard user cannot focus, containing nothing a keyboard user can focus. That is the same defect with the last accidental workaround taken away, not a different one. `codex` found it during 0033's icon-only work and it was correctly declined there as out of scope: making every card's tile a control is not an icon-only option's business.

## Requirements

### Testing Requirements

Per [architecture — Testing & Quality Conventions](../specs/architecture/index.md#testing--quality-conventions):

- `npm test`, `npm run lint`, `npm run typecheck` MUST pass; `codecov/patch` 100%; `codecov/project` no regress.
- **Assert the role and the accessible name, never the tag.** `expect(el.tagName)` passes on a `<button>` with no name, which is a worse tile than the div it replaced — it is focusable, announces "button", and says nothing about what it does. The assertions MUST go through the accessible tree (`getByRole('button', { name: … })`).
- **The existing pointer-gesture suite MUST pass unmodified.** `GridCard`'s tests already pin tap, hold, double-tap, edit-mode suppression, the portalled-descendant case and the embedded-control case; the element under them is what changes. A test that had to be edited to stay green is a behaviour change and MUST be justified as one in the PR, not absorbed as a fixture update.
- **A tier that embeds controls MUST be covered, not only `glance`.** The nesting case is what the element decision turns on, and a suite exercising only the tier with nothing inside it would pass on a choice that is invalid markup everywhere else.
- **Keyboard activation MUST be asserted for each action the tile carries**, including whatever route the contract gives `holdAction` and `doubleTapAction`. A test covering only the primary action would pass on a tile whose `glance` detail dialog is unreachable without a pointer — which is the operability rule failing in a new place rather than the old one.
- **`Retry` MUST be asserted to re-dispatch the identical command, gated.** One test that it reaches Home Assistant a second time, and one that a card whose options impose a confirmation gate still gets the gate — a recovery path that skips `confirmOption`'s dialog is a security regression, and it is the plausible shortcut.
- **`Retry` MUST be asserted against the at-most-once guard, in all three directions**: refused while the guard's window is genuinely open; admitted rather than silently swallowed in the case this change exists for; and **refused after a failure whose outcome is ambiguous**, which is the direction that matters — a test covering only the first two passes on an implementation that releases the guard on any `success: false` and therefore double-actuates.
- **`Dismiss` MUST be asserted to dispatch nothing.** It clears a presentation state; a `Dismiss` that also actuates is the opposite of what the user asked for.
- **A card whose error is not a failed service call MUST be covered** — `CameraCard`'s stream error is the concrete one. Whatever PR 1 decides it offers, a suite exercising only `useServiceCall`'s error would pass on a `Retry` that is inert or absent there without anything saying so.
- **The focus treatment MUST clear the workshop's accessibility baseline**, which runs `@storybook/addon-a11y` on every story. A focus indicator that fails contrast is not an indicator.

Skipping or weakening any rule to land the PR is a bug in the PR.

### Functional requirements

[design-system — size-adaptive layouts](../specs/design-system/index.md#size-adaptive-layouts) owns the error-tile contract and the no-operability-regression rule, and [options/common — action type](../specs/entity-cards/options/common.md#action-type) owns the gesture vocabulary and the dispatch guarantees — this change's acceptance criteria, not restated here. What implementing them requires of this change:

- **The spec MUST distinguish the two error surfaces and say which rule binds which.** As written, one sentence about "a `glance` error tile" is held by `ErrorDisplay` and not by the shell, and nothing records that there are two. Fixing the shell without stating the distinction leaves the next reader in the position this change started from.
- **The contract MUST reach every tier, not only `glance`.** The spec pins `glance` because that is where the tier drops things; the shell's error state renders at all four, and a `full` card whose service call failed has no `Retry` either. The tier is where the contract was written, not the limit of what it is for.
- **Keyboard equivalents MUST be defined for the gestures the tile carries, or their absence justified.** `tapAction`, `holdAction` and `doubleTapAction` are three routes off one surface, discriminated by pointer timing — 500ms and a 250ms window — and a keyboard has neither. The default pair is `tap → toggle`, `hold → more-info`; a tile that maps only the primary action leaves a `glance` card's detail dialog, and therefore that card's controls, pointer-only. The no-operability-regression rule is written about tiers, but a modality that reaches one action of three fails it the same way.
- **How a screen's worth of tiles is traversed MUST be settled, not left to the element choice.** A dashboard is a wall of tiles and making each one a tab stop is a decision with a cost; so is the alternative. Whatever the answer, it belongs in the spec rather than falling out of whichever element PR 2 picks.
- **`Retry` reads like the thing the dispatch guarantees forbid, and the reconciliation MUST be stated rather than left to the reader.** [options/common — action type](../specs/entity-cards/options/common.md#action-type) rules out routing a consequential command through a retrying wrapper. A user pressing `Retry` is a new gesture and is therefore compatible; an automatic or implicit re-send is not. Every reviewer of the PR implementing this will raise the objection, so the contract has to answer it where `Retry` is specified.
- **`Retry` MUST survive the at-most-once guard where it is safe to, and MUST NOT where it is not.** `guardedDispatch` keys on `domain.service:target:data` and holds the entry until the entity transitions or `ACKNOWLEDGEMENT_TIMEOUT_MS` (2000ms) elapses, releasing on neither a failure nor a rejection (`guardedDispatch.ts:192–230`). A failed command therefore leaves its key pending, and an immediate `Retry` of it is refused, resolves to `null`, and does nothing the user can see. **The obvious correction — release the guard whenever the dispatch reported failure — is unsafe and MUST NOT be taken.** `callServiceOnce` collapses a transport rejection into `{ success: false }`, and a rejection after Home Assistant has already accepted the command is indistinguishable there from one before it was sent. Releasing on that reading lets `Retry` press a button twice, skip two tracks or move a cover twice, which is the exact harm [options/common](../specs/entity-cards/options/common.md#action-type)'s non-retrying rule names. The contract MUST therefore separate a **provably undispatched or definitively refused** failure, where the key may be released and `Retry` admitted, from an **ambiguous** one, where the guard MUST hold and `Retry` MUST tell the user why it is waiting rather than silently resolving to nothing. Which outcomes fall on which side is PR 1's to settle and may require the dispatch layer to report more than a boolean.
- **The recovery actions offered MUST match the failure's source.** With `isError` covering a failed command, a stream that would not start and a pre-dispatch refusal alike (see Motivation), `Retry` MUST NOT be specified as "repeat the command" universally — for a state with no command to repeat that is unimplementable, and a `Retry` button that cannot retry is worse than none. Either the failure carries what recovers it, or the contract scopes `Retry` to the service-call state explicitly and says what the others offer instead. `Dismiss` is the one action every source can support.
- **The `title` tooltip is what the shell uses today**, and the contract already rules it out as the mechanism. It MAY remain as a sighted-hover convenience, so what this change owes is a replacement carrier, not its removal.
- **Every card MUST get this from the shell.** The shell owns the tile, the gestures, the detail dialog and the confirmation gate already; a change that needs an edit in twenty-five card files to hold a universal contract has been put in the wrong place — which is the same reasoning [0033](./0033-icon-only-cards.md) used for the accessible name.
- **Edit mode is a constraint on the element choice, not a target of it.** [entity-cards](../specs/entity-cards/index.md) owns what a press does there; what matters here is that the tile is also the grid's drag target, so a control that grabs focus or swallows the drag would trade an accessibility fix for a broken editor.

## Design Decisions

The element the tile becomes is **PR 1's decision, not this document's** — it is a design-system contract every card and every theme inherits, and settling it inside a fix would settle it by accident. The routes it is to be chosen among, with what each costs:

- **(A) A native `<button>` at every tier.** Real focus, real activation, a name, and no invented semantics. Its cost is the content model: cards embed sliders, steppers, switches, select triggers and text fields at `row`, `tall` and `full`, and interactive content inside a `<button>` is invalid markup whose focus and announcement behaviour is not defined by anything. `ErrorDisplay` can take this route precisely because its `glance` tile contains nothing.
- **(B) A native `<button>` only where the tile has no interactive descendants.** Correct in both cases and conditional on content, so the tile's element changes with the tier and with a card's options — a card MUST NOT derive that from measuring itself, so what decides it has to come from somewhere that already knows.
- **(C) `role="button"` and `tabIndex` on the div.** Keeps one element and one class. It buys nothing that (A) does not, and it has (A)'s nesting problem in the accessibility tree without (A)'s browser-provided focus ring and activation, so it trades a defined invalid markup for an undefined valid one.
- **(D) A dedicated focusable child carries the tile action** and the tile stays a non-interactive container. Sidesteps nesting entirely — the control is a sibling of the embedded controls rather than their ancestor — at the cost of a part that exists for assistive technology and must be positioned and styled to look like nothing, on every theme.
- **(E) Ruled out — leave the tile as it is and give only the error state a focusable affordance.** It satisfies the letter of the error contract and leaves every card's primary action pointer-only, which is the larger defect and the one the error contract only happens to expose. A fix that makes the failure state reachable and the working state not is the wrong shape.

Three decisions this change does take:

- **The contract is settled before anything implements it.** Same reasoning as [0042](./0042-tall-tile-control-geometry.md) PR 1, and the same evidence: routes (A) through (D) differ in what a theme can style and what a card may contain, so choosing one in a diff that also moves the press pipeline reviews as a bug fix and lands as an architecture change.
- **Operability first, error recovery second.** The error contract's three halves all presuppose a tile that is a control, so the tile becomes one and the error work is built on it. Sequenced the other way, the error state gets a bespoke affordance that the general fix then has to remove.
- **`Dismiss` ships with the surface and `Retry` follows on its own.** `Dismiss` is a call to a `clearError` that already exists; `Retry` has to hold the command that failed, re-enter the confirmation gate and get past the at-most-once guard, which is the only genuinely new mechanism in this change. Splitting them keeps that mechanism reviewable on its own rather than as the second half of a dialog PR.

## Tasks

- [x] **PR 1 — Settle the tile's control contract** (spec only, no source changes): choose among routes A–D and record why; design-system states what the shell tile is in the accessibility tree, what carries its name, how a screen's tiles are traversed, and what focus indication it owes; the keyboard route for each of the three gestures, or the recorded reason a gesture has none; the two error surfaces distinguished, with the error-tile contract stated for every tier rather than only `glance`; `Retry` specified against the non-retrying dispatch rule it superficially contradicts, including which failure outcomes release the at-most-once guard and which are too ambiguous to; which recovery actions each source of the error state owes, given that `isError` covers more than a failed command; changelog entries on design-system and options/common
- [x] **PR 2 — The tile becomes a control**: implement PR 1's element decision in the shell for the primary action only, with focus indication in the anatomy; the existing pointer-gesture suite passing unmodified; keyboard-activation and accessible-name coverage at `glance` and at one tier that embeds controls; edit-mode selection and drag unchanged
- [x] **PR 3 — Keyboard routes to the hold and double-tap actions**: implement what PR 1 settled for the two secondary gestures, so a `glance` card's detail dialog and a card's `doubleTapAction` are reachable without a pointer; coverage per route, including a card whose `holdAction` is `none`
- [x] **PR 4 — The detail dialog carries the failure, and `Dismiss`**: the shell passes the current failure message and the recovery actions to `EntityDetailDialog` while `isError` holds, and pressing the tile in the error state reaches it at every tier; `Dismiss` clears the error and dispatches nothing; the `title` tooltip is no longer what carries the message; coverage including an icon-only tile, whose accessible name already carries the message and whose press had nowhere to go
- [x] **PR 5 — `Retry` re-dispatches the command that failed**: for the service-call state only, per PR 1's scoping — the failed dispatch is retained so the recovery action can repeat it, through the confirmation gate and through the at-most-once guard rather than around either, implementing PR 1's boundary between a failure that releases the guard and an ambiguous one that does not; coverage for the gated case, the guard-refused case, the guard-admitted case and the ambiguous-outcome case
- [x] **PR 6 — Reconcile the stand-in error tile with the shell's**: `ErrorDisplay variant="card"` implements the contract in a second place and its callsites then withhold the actions — no production callsite passes `onDismiss`, and the entity-not-found path passes no `onRetry` — so the tile renders a button onto a message the user cannot act on. Fold it onto the shell's, or record why a tile that stands in for a card is not a card tile; either way the rendered tile ends the PR actually offering the recovery actions, rather than merely being a component capable of rendering them.

  **This PR is closing a stated MUST, not choosing between two defensible treatments.** [design-system — size-adaptive layouts](../specs/design-system/index.md#size-adaptive-layouts) already requires it: "The states a card renders **instead of** itself — loading, error, unavailable — are tiles like any other and MUST take the tier of the card they stand in for". The two tiles that go through `ErrorDisplay variant="card"` — not-found and disconnected — stamp **no `data-tier` at all**, so they are not merely unthemed, they render at the wrong size in breach of that MUST. They also stamp no `liebe-card`, which is the theming handle; both attributes are missing together and for the same reason.

  **Keep those two claims apart, because conflating them is what produced an error here.** _Bypasses `GridCard`_ is true of **all three** lifecycle tiles — which is why none of them carries the shell's edit affordances, the finding this task exists for. _Lacks `liebe-card` and `data-tier`_ is true of **two**. The skeleton is the one already compliant: `SkeletonCard` renders `<div className="liebe-card" data-tier={tier}>` directly and deliberately, "so a theme reshapes the loading tile with the loaded one". **That gives this task its target shape rather than a design decision to make** — one of the three already does the right thing, so the direction is "make the other two consistent with it", and the remedy may be as small as stamping the same two attributes, without making a stand-in tile a `GridCard` and without handing a card whose entity is merely pending the delete and configure affordances. It is measurable now, and was measured the hard way: change [0037](./0037-card-state-and-capability-correctness.md) PR 3 shipped `CoverCard`'s `UnknownEntity` story with `expect(canvasElement.querySelector('.liebe-card')).toBeInTheDocument()`, which was **right about the contract and red against the code**. Nothing ran it — story `play` functions were not executed until [0040](./0040-test-harness-reliability.md) PR 6 made them a gate — so the two landed hours apart, each green alone, and main was broken by the pair. That assertion has been repointed at what the tile says (`Entity Not Found`, and that it names the entity) to unbreak main, and **this PR owns putting a shell assertion back** — on whichever of the three states it decides the contract covers, or a recorded reason there is not one. The repointed story is deliberately weaker on this exact point than its predecessor, and that is the debt this line exists to keep visible.

- [x] **PR 7 — A toggle route on an unavailable tile reaches the dialog**: `useCardActions` redirected only the card's _default_ to `more-info` while `unavailable`, and suppressed a resolved `toggle` at dispatch — `performDispatch` returns early for that route before it would consult the card's `onToggle`. So a **stored** `tapAction: toggle`, which never consults the default, dispatched nothing **and opened nothing**: the tap did nothing at all, on a tile where at `glance` the tap is the only affordance. Redirect at resolution instead, so every route that resolves to `toggle` becomes `more-info`, which also makes the tile report itself actionable and stops the confirmation gate offering "Turn on …" in front of a dialog that switches nothing; hook-level tests for the stored tap, hold and double-tap routes, that the card is never consulted, that a non-`toggle` route is untouched, and a positive control on the same card once available

  **Why this is not PR 6.** PR 6 owns a _rendering_ question — whether a lifecycle tile belongs inside the card shell. This is dispatch routing in a shared hook, and the two surfaces do not even overlap: the tile this is live on is the **inoperable-state tile**, a real `GridCard` raising `isUnavailable` from inside, which PR 6 would not touch even after it lands. Measured on change [0037](./0037-card-state-and-capability-correctness.md) PR 7, where asserting the dialog on that route failed with `Unable to find role="dialog"`. It belongs to every domain's inoperable tile, not to the card it was found on

- [x] **PR 8 — A gesture armed while available fires after the entity goes quiet**: the hold timer and the double-tap timer capture the resolution made when the gesture started, so an entity that becomes `unavailable` inside that window is still dispatched the `toggle` — `onToggle` is called against a device whose state is now indeterminate. Re-read availability where the deferred work executes, or cancel and re-resolve pending gestures when it changes; the same question applies to a confirmation dialog left open across the transition. Coverage for the hold window, the double-tap window and the open-confirmation case.

  **Pre-existing, and the measurement says so.** Raised by `codex` on PR 7 as a regression that PR 7 introduced by removing `performDispatch`'s `if (unavailable) return`. It is not: the guard read the `unavailable` **captured in the timer's closure**, not the current one, so it was never execution-time protection. The same probe — arm a hold while available, flip to unavailable, advance the timer — calls `onToggle` exactly once on PR 7's branch **and on `main` before it**, bit for bit. What PR 7 removed was a check that could not fire; this is the gap it was mistaken for, and it is a gesture-lifecycle change rather than a routing one

**Sequencing.** PR 1 lands first and everything after it is an application of what it settled; taken in any other order, the first fix to touch the tile decides the element for every card and every theme without the decision being visible. **PR 2 MUST NOT be folded into anything.** It changes the element every card renders into and it sits under the press pipeline that tap, hold and double-tap all route through, so it is the one PR whose regression surface is the whole product — and its own evidence is a suite it did not modify, which only reads as evidence when nothing else in the diff could have moved. PR 3 follows PR 2 because it needs a focusable tile to route keys to. PRs 4 and 5 both need PR 2 as well, and PR 4 precedes PR 5 because `Retry` needs a surface to be offered on; they are not folded together because `Dismiss` is a call to an existing function and `Retry` is a new mechanism, and a PR containing both would be reviewed as the easier one. PR 6 is last: it is the same contract applied to a surface that already satisfies the old reading of it, and its answer depends on what PR 2 made the shell.

## Out of Scope

- **Keyboard drag-and-drop in edit mode.** Moving and resizing cards from a keyboard is react-grid-layout's interaction model, a separate capability, and not what the error contract or the primary action needs. Edit mode's existing behaviour is a constraint here, not a target.
- **`hassService`'s internal attempt schedule.** It is the transport's, it is not what `Retry` is, and [options/common](../specs/entity-cards/options/common.md#action-type)'s non-retrying rule already governs which path a consequential command takes. Nothing here changes it.
- **How each card renders its error inline** — a light's `ERROR` state line, the vacuum's alert glyph. The message the tile carries is the shell's; what a card draws in its own layout stays that card's.
- **The per-card `ErrorBoundary` convention** ([0041](./0041-card-conventions-and-reference.md)). A component that threw is a different failure from a service call that was refused, and 0041 settled its convention already.
- **The icon-only accessible name** ([0033](./0033-icon-only-cards.md) PR 1). Shipped, correct, and the half of `common.md`'s rule that is done; this change owns the other half of the same sentence.
- **A general accessibility audit of the panel** — the sidebar, the configuration dialogs, the entity browser. This change is the card tile and what the error contract needs of it. [0035](./0035-light-appearance-contrast.md) owns the accessible-name residue on the embedded controls.
