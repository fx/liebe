# 0040 — Test & CI Harness Reliability

## Summary

Five defects in the machinery that decides whether Liebe's code works, grouped because they share a failure mode rather than a subsystem: each produces a result that **looks like a pass and is not one**. The e2e harness runs one shared stack per machine whose bind mounts point at whichever worktree last brought it up, and it has already published a green 9/9 that executed entirely against another branch's bundle. Roughly two hundred Storybook `play` functions assert and nothing executes them — one of them has been wrong since it was written. Three test files flake under concurrent load and one leaks a timer past teardown, throwing an unhandled error while the suite reports green. And `react-hooks/set-state-in-effect` is configured as `error` but only matches bare `useEffect(...)`, so five `React.useEffect` member calls are invisible to it.

**Spec:** [architecture](../specs/architecture/index.md) → [testing & quality conventions](../specs/architecture/index.md#testing--quality-conventions), with the story-runner half in [storybook → CI & publishing](../specs/storybook/index.md#ci--publishing) · **Status:** draft · **Depends on:** —

Supersedes issues [#208](https://github.com/fx/liebe/issues/208), [#244](https://github.com/fx/liebe/issues/244), [#259](https://github.com/fx/liebe/issues/259), [#264](https://github.com/fx/liebe/issues/264), [#276](https://github.com/fx/liebe/issues/276).

## Motivation

`AGENTS.md` already states the principle these violate: _a probe that fails tells you something; a probe that passes tells you nothing until you have established it could have failed._ Every item here is a passing signal that could not have failed.

**The e2e harness.** `ha/docker-compose.yml` resolves to a single fixed project (`ha`, containers `liebe-e2e-ha` and `liebe-e2e-go2rtc`), so there is exactly one stack per machine and its bind mounts point at whichever worktree last ran `up`. Two checkouts running e2e concurrently silently serve each other's panel bundle and Home Assistant configuration. This is not hypothetical: worktree A built its bundle and ran its suite, worktree B recreated the containers against itself because it needed an `input_text` helper defined only in its own `configuration.yaml`, and A then re-ran the full suite and reported **9/9 passing** — every run executed against B's bundle and B's config. One of A's three new specs has still never run against A's own code. A's runs also mutated shared state on B's instance (`input_boolean.e2e_flag`), so B's results in that window are equally suspect and would have presented to B as unexplained flakiness in its own feature. The false pass was published in a pull request description before being caught. Neither side did anything unreasonable: the harness offers no way to tell whose stack you are talking to, and a contaminated run looks exactly like a clean one.

Separately, `npm run e2e:ha:up` cannot run as scripted — the invoking user is not in the `docker` group and a fresh workspace has no running daemon, so the documented path fails with a permission error on the socket. `AGENTS.md` now documents the `sudo service docker start` / `sg docker -c` workaround, which keeps people working and leaves the scripted path that the change documents point at still broken.

**Storybook `play` functions.** There is no story test-runner wired up, `*.stories.tsx` is excluded from coverage, Vitest collects `*.{test,spec}.*` only, and `build-storybook` proves compilation. The assertions read as tests to anyone reviewing a PR and were requested as tests in the coder briefs. The framing "an assertion that stopped asserting would be caught by nobody" turned out to understate it: the `Off` story in `MediaPlayerCard.stories.tsx` has been **wrong and failing since it was written**, asserting a `Turn on` pill against a fixture whose mask had bit 128 clear so no primary pill rendered. Verified by rendering that exact entity in a throwaway spec — red before the fixture fix, green after. That file's meta docblock states "Every story asserts rather than merely rendering", which is true of the code and false of the pipeline; its other ~19 play functions are unverified in both directions.

**The flakes.** Three files have flaked under concurrent load, none related to the diff being pushed: `ConfigurationMenu.test.tsx` with `window is not defined` after teardown, `WeatherCard.configSave.test.tsx` failing at 5987 ms, and `CardConfig` weather + `BinarySensorCard` config modal timing out at ~5 s under coverage instrumentation and passing with `--testTimeout=30000`. The duration evidence points at a class rather than three bugs: **tests with ~5 s implicit timeouts that only hold when the suite has the machine to itself** — the failing weather run took 50 s wall against 15 s for passing runs of the same commit, on a one-line markdown change. Coverage instrumentation pushes them over the same edge with no concurrency at all. `CardConfig.alarm.test.tsx` failed once on a documentation-only run and has never reproduced; whether it is a fourth instance of that class is an **untested hypothesis**, and it is recorded as one deliberately, because an issue saying "probably the same as #264" reads three weeks later as though someone checked.

`ConfigurationMenu`'s timer is a genuine bug rather than a timing sensitivity: a 3-second `setTimeout` outlives the test that scheduled it and throws after teardown regardless of how fast the machine is — as an unhandled error rather than a test failure, which is why the suite reports green while the process still fails. It failed a pre-push hook on a markdown-only diff, in the one place with no CI log to inspect afterwards.

**The lint rule.** `GridCard.tsx` writes `React.useEffect(...)`, which the rule does not match, and there is at least one real instance: `React.useEffect(() => { setDetailFor(null) }, [...])` — exactly the pattern the rule exists to reject. The cover card needed the same behaviour for change [0019](./0019-cover-fan-cards-to-spec.md), could not use the effect form because written as `useEffect(...)` the rule fires, and used the repo's lint-clean alternative instead. So the shell and the cards solve one problem two ways and the difference is not a decision anyone made: one of them was invisible to the linter. Five `React.useEffect` calls exist across `GridCard.tsx`, `ActionEditor.tsx` and `CardConfig.tsx`, and only one has been inspected.

## Requirements

### Testing Requirements

Per [architecture — Testing & Quality Conventions](../specs/architecture/index.md#testing--quality-conventions):

- `npm test`, `npm run lint`, `npm run typecheck` MUST pass; `codecov/patch` 100%; `codecov/project` no regress.
- **Every gate this change adds MUST be shown to fail.** A new gate that has only ever been observed green is the exact defect being fixed. Each PR MUST demonstrate its gate rejecting a deliberately broken input — a mismatched bundle, a wrong assertion, a `React.useEffect` writing state — and record that evidence.
- The bundle-identity check MUST be verified by an **actual mismatch**, not by reasoning: point the check at a stale bundle and show it throws with both hashes in the message.
- The story runner's first run MUST be treated as a discovery pass, not a pass/fail gate: roughly 200 previously-unexecuted assertions are expected to surface real failures. Each MUST be triaged as a wrong assertion or a real defect and recorded, and the PR MUST NOT delete a failing assertion to go green without saying which it was.
- Timeout changes MUST NOT be used to mask a leak. Raising `testTimeout` addresses the load-sensitivity class; the `ConfigurationMenu` timer MUST be fixed separately and MUST NOT be reported as fixed by a timeout change.

Skipping or weakening any rule to land the PR is a bug in the PR.

### Functional requirements

[architecture](../specs/architecture/index.md) owns the testing conventions, the coverage gates and the CI job set; [storybook](../specs/storybook/index.md) owns what stories are for — this change's acceptance criteria, not restated here. What implementing them requires of this change:

- **Both e2e fixes ship, and the identity check ships regardless.** Parameterising `COMPOSE_PROJECT_NAME` per checkout prevents the collision; the identity check makes any future collision **loud**. Fail-closed beats relying on discipline, and the check retains its value after the project name is parameterised.
- **The identity check MUST work over HTTP alone.** Asserting mount sources via `docker inspect` would be unavailable in exactly the environment where the contamination happened — the runner there cannot reach the docker socket without `sudo`. Hashing the served bundle and comparing against local `dist` needs no privileges and is conclusive on its own. Roughly 15–30 lines in `tests/e2e/global-setup.ts`, no new dependencies.
- **Hash the URL `configuration.yaml` actually points `module_url` at**, not a hardcoded `/local/dist/panel.js`. `tests/e2e/panel-loads.spec.ts` already parses that file for its own assertion, so the pattern exists; hardcoding the path would give the harness two sources of truth about where the bundle lives.
- **The skip MUST be an allowlist, not "anything that is not the mounted bundle".** Pointing e2e at the dev server on `:3000` is a legitimate workflow that would mismatch honestly, so that documented endpoint is exempt. Everything else **fails closed** — a stale path, a foreign host, or an unexpectedly remote bundle is also "not the mounted bundle", and skipping on that basis would re-admit the exact contamination this check exists to catch, silently and with a green tick. Both branches MUST be tested: the allowlisted dev-server URL skips, an unrecognised URL fails.
- **Ports follow the project name.** They are currently fixed too, so per-worktree stacks need per-worktree ports or they collide on bind instead of on mount.
- **The scripted startup MUST either work or fail loudly naming the cause.** A silent-ish permission error that people route around by hand is how a documented workflow rots. Detecting an unreachable daemon and exiting with a message that names it is acceptable; leaving the script to fail with a raw socket error is not.
- **The story-runner PR MUST also settle what stories are for.** If they stay documentation-grade, the coder briefs stop asking for "stories that assert" and the assertions move into the render-level tests that do run — roughly half duplicate a `__tests__` case already. If they become gate-grade, the storybook spec's CI section says so and the cost is accepted explicitly. Wiring a runner without settling this leaves ~200 slow assertions of undecided status in CI.
- **The lint fix and the cleanup are separable and MUST be sequenced.** Make the rule see member calls (or ban `React.useEffect` in favour of the imported form so the existing rule applies) first; then fix what it finds. Expect instances beyond the one inspected.
- **`AGENTS.md`'s e2e section MUST be reconciled** with whatever the scripts do afterwards. It currently documents a manual workaround as the working path; a fixed script makes that guidance wrong, and stale guidance about a gate is how the next contaminated run happens.

## Design Decisions

- **The hash check is preferred over asserting mount sources**, for a reason beyond taste: it works purely over HTTP and needs no docker privileges, so it is available in the environment where the contamination actually happened. A check built on `docker inspect` would be absent exactly there.
- **Both e2e fixes rather than either.** The project-name fix alone leaves the class silent if it recurs through some other route; the identity check alone leaves two worktrees fighting over one stack and merely tells them so. Together they make the collision impossible and any residual mismatch immediately fatal.
- **`CardConfig.alarm.test.tsx` is investigated, not assumed.** It is filed with no diagnosis on purpose — a guessed cause directs the next person's search. It MUST be checked for a timing-sensitive wait before being treated as an instance of the load-sensitivity class, and if no cause is found the honest outcome is to say so and leave it open rather than close it as "same as the others".

  **Outcome (PR 5): it has no timing-sensitive wait, because it has no wait at all.** The file contains no `async`, no `await`, no `waitFor`, no `findBy*`, no `user-event` and no fake timers; every one of its seven tests is a synchronous `render` of the configuration modal followed by synchronous `getByText`/`queryByText` queries, and the two effects `CardConfig` runs are synchronous state writes with no timer or subscription. There is therefore nothing in it that _can_ wait, which leaves its own render as the only thing able to consume a budget — so it belongs to the load-sensitivity class by elimination rather than by resemblance, which is the distinction this bullet asked for.

  It is, however, the **least** load-sensitive of the specs measured: its worst test ran 695–916 ms across four ordinary coverage runs and 1807 ms under deliberate oversubscription, against 4923 ms for `WeatherCard.configSave.test.tsx` on the same run. Its one recorded failure is thus a bigger outlier than the others' and is **not** fully explained by slowness alone — a ~5x excursion over its measured worst has no established cause. Raising the default covers it with room to spare either way, so the residual question is recorded rather than closed: if this spec times out again at 20 s, the load-sensitivity explanation is wrong for it and it needs its own diagnosis.

- **The class has a fifth member, and it is the one that sets the number.** `CardConfig.controlStyle.test.tsx` → "leaves the key absent when an unrelated field is edited and saved" timed out at **5464 ms** against the 5000 ms default under coverage instrumentation, then passed in isolation 7/7 and on a full re-run — the same signature as the files named above, and not one of them. It matters because it is the second timeout recorded with a **measured duration**, so the timeout is chosen against two independent observations (5464 ms and `WeatherCard.configSave.test.tsx`'s 5987 ms) rather than one. PR 5's own runs reproduce both as the worst default-governed test in at least one run apiece, which is what makes them the class's worst members rather than two anecdotes.

- **The fifth site was invisible for a reason worth naming, and the reason is general.** PR 3 established empirically that `CardConfig.tsx`'s `Modal` reported nothing whatever form the call took — a deliberately blatant `setLocalConfig({})` in a bare `useEffect` was silent there while the same violation in a fresh component in the same file reported fine — and sent PR 4 to audit it by reading. PR 4 reproduced that and then found the cause: **the component carried a `// eslint-disable-next-line react-hooks/exhaustive-deps` comment**, which is one of the directives the React compiler treats as "the author knows they are breaking the rules of React", so it bails on the enclosing function and every compiler-backed rule goes quiet with it — `set-state-in-effect` included.

  Verified in both directions rather than inferred. Removing only that comment from `main`'s file made the `Modal`'s real effect **and** a planted one both report. Adding such a comment to `useCameraStreamStatus.ts`, which was analysing correctly, silenced a planted violation there **and** turned that hook's own genuine `set-state-in-effect` suppression into an "unused eslint-disable directive" warning — the rule had stopped reporting for the whole function, which is what makes the blind spot self-concealing: the suppression that proves the rule once worked there reads afterwards as though it never needed to.

  The consequence for the gate: **a `react-hooks/exhaustive-deps` suppression is not local to the line it sits on — it disables the compiler-backed rules for the entire function containing it.** PR 4 removed `CardConfig`'s along with the effect, so that component is analysable for the first time (a planted violation in it now reports). Two remain, both in `src/theme/`: `tokens.stories.tsx` and `customCss.stories.tsx`, each a deliberate dependency-less effect that reads computed styles off a live element. Neither is a defect — that read genuinely cannot happen during render — but each is a function the rule cannot see into, so a future violation beside them would land unreported. Closing them means an explicit `set-state-in-effect` suppression in place of the blanket one, and it is **not** in PR 4: they are story helpers rather than the shell, and that task's scope is the five call sites. It is **PR 7**, which is where the mechanism above is restated for someone reading the task list rather than this section — only `exhaustive-deps` was tested as a bail trigger, `set-state-in-effect`'s own suppression does not bail (which is what makes the replacement a fix), and `rules-of-hooks` is untested.

- **A render-phase reset and an effect one are indistinguishable from anywhere a normal test stands, and PR 4's evidence had to be taken from somewhere else.** Both settle on the same DOM, and React Testing Library flushes passive effects at every `act()` boundary, so an assertion made after one agrees with either spelling — PR 4's first six regression tests passed unchanged against the merge-base implementation, which makes them guards against the reset being _removed_ and not evidence for this change. The difference is the commit in between, and a **layout** effect is the one vantage inside it: it runs after that commit's DOM mutations and before anything passive.

  Three tests observe from there, one per site, and each was shown to fail against the merge-base implementation restored in place — `GridCard.dialogReset.test.tsx` (2 failed of 8), `CardConfig.itemReseed.test.tsx` (1 of 5), `ActionEditor.test.tsx` (1 of 24). What they catch is a real frame rather than a theoretical one: a card recycled onto another entity committed the previous entity's dialog over the new one, the configuration modal committed the previous card's body under the new card's title, and the action editor committed the service of the action it had just stopped pointing at.

  Note which half of the change this does **not** apply to. On edit mode the shell's reset is a re-spelling and nothing more: the `!isEditMode` render guard already covered the commit the effect ran late by, so there was never a frame to catch. Claiming otherwise — as `CoverCard`'s reasoning invites, since it had no reset at all — would be describing a bug this shell did not have.

- **Raise `testTimeout` and fix the timer, as two things.** The instrumented run passing at 30 s is evidence that those assertions are correct and merely slow, which a timeout addresses. The `ConfigurationMenu` timer fires after teardown on any machine, which a timeout does not address and would hide. Conflating them would leave a real bug behind a config change.
- **The story-runner decision is a CI-semantics change, which is why it was never folded into a card PR.** It changes what a green CI run means for a dozen card families' worth of story matrices, and that is a decision to take deliberately with its cost stated.

  **Outcome (PR 6): gate-grade, and the cost is what settled it.** The choice was never really "assertions or no assertions" — it was whether executing them is worth a browser. It is not, because it does not need one: Storybook's portable-stories API composes a story with the real `.storybook/preview` annotations, so `src/__tests__/stories.test.tsx` renders and plays all **656** stories inside the Vitest suite that already runs. Measured, three paired full-suite runs without → with: 25.1 s → 37.1 s on the first cold pair, then 22.3 s → 22.2 s and 22.2 s → 23.1 s. The file's own tests cost about 9 s of CPU and it is one worker among 253, so the steady-state wall clock rises by **under a second**. A `@storybook/test-runner` job would have cost a Playwright install, a static build to serve and minutes of its own — for the same assertions. Documentation-grade was the other live option and loses on the same arithmetic: it would have retired ~340 assertions and rewritten the survivors into `__tests__` for days of work, to end with strictly less checking than a second of CI buys.

  **The first run's 23 failures, each triaged.** No assertion was deleted to go green.
  - **Ten wrong assertions, now corrected.** Six in `MediaPlayerCard.stories.tsx`, where the `transport()` helper read _every_ `.liebe-pill` on the card, so the volume mute pill broke every exact-list assertion the moment mute shipped — the helper is now scoped to the `Media controls` group. `WeatherCard/ExceptionalCondition` asserted a `⚠️` emoji that change [0030](./0030-weather-forecast-legibility.md) retired along with `getConditionEmoji`; the card draws the line-art `TriangleAlert`, and the story now asserts that. `FanCard/WithoutPercentage` asserted `ON` where the spec gives the primary slot to the preset (`fan.md` — "the bare state/preset"), and the fixture has one. `EntityDetailDialog/BooleanControl` clicked the switch and expected it to flip, which a control driven by entity state cannot do against a workshop that pushes no state back — it now asserts the dispatch. `CameraCard/OverlayWithoutState` asserted the `LIVE` badge _outside_ the `waitFor` that waits for the overlay, a race its sibling story avoids.
  - **Five jsdom cannot evaluate**, named in the runner's `BROWSER_ONLY` map with reasons: two forecast-width stories, two sensor-graph ratio stories, one slider drag. They measure rendered boxes, and jsdom lays nothing out. This is the class the change document already had a concrete instance of — `ForecastsMaxCountOnMinimumWidthTile`, shipped to gate-grade standard by change [0030](./0030-weather-forecast-legibility.md) and never executed — and the run confirms **why** it never could have been: its `>= 44px` assertion fails on a 0-wide box while its no-overflow neighbour _passes_ on `0 <= 1`. Left unenforced, tracked in [docs/tasks.md](../tasks.md), and the map is self-verifying: each listed story is still executed and must still throw, so an entry that goes stale is reported rather than skipped forever.
  - **Seven were the runner's own gap, now closed.** Every `CameraCard` stream story sat in `CONNECTING`, because the workshop substitutes the stream-readiness hook through a Vite plugin the runner did not reproduce, and because jsdom neither fires `load` on an `<img>` nor reports a decoded size. The runner now applies the same substitution and serves images off `.storybook/public` — resolving the real file, so the deliberately-missing frame still produces `error` and the stream-error story stays honest.
  - **One is a finding worth keeping.** `ActionCard/Activating` rendered the success check while asserting the in-flight spinner, and only when other stories ran first. The cause is not the card: `guardedDispatch`'s pending set is process-wide by design, so the story's deliberately-unsettling call left that command in flight and the **next identical command was admitted as a success**. Any suite that lets a service call hang inherits this; `resetDispatchGuard()` per story is the fix, and it is recorded in `AGENTS.md` because the failure it produces looks exactly like a card defect.

  **No _card_ defect surfaced** — the harness defects above are real and are the run's findings; what the ten corrected assertions did not turn up is a single case of product code behaving wrongly. That is the honest result rather than a comfortable one: every one of the ten wrong assertions was checked against the spec or an existing `__tests__` case before being corrected, and in each the code was right and the assertion had been written against a behaviour that either changed afterwards or never existed. It is also the expected shape — these stories were reviewed as tests even while unable to run, so what rots in them is the assertion, not the card.

- [x] **PR 3 — Lint sees member-call effects**: `react-hooks/set-state-in-effect` matches `React.useEffect`, or `React.useEffect` is banned in favour of the imported form; demonstrated firing on the `GridCard.tsx` `setDetailFor(null)` case
- [x] **PR 4 — Fix what the rule finds**: move the shell's state-writing effects to the render-phase pattern the cards already use; audit all five `React.useEffect` call sites, not only the inspected one
- [x] **PR 5 — Suite timeout and the timer leak**: clear `ConfigurationMenu`'s timer on unmount; raise the default `testTimeout` to cover the load-sensitive class; run the full suite under coverage instrumentation as evidence; investigate `CardConfig.alarm.test.tsx` for a timing-sensitive wait and record the finding either way
- [x] **PR 6 — Story assertions run, or stop pretending to**: decide whether stories are gate-grade or documentation-grade and record it in the storybook spec's CI section; if gate-grade, wire a story runner into CI and triage every failure the first run surfaces as wrong-assertion or real-defect; if documentation-grade, move the assertions into render-level tests and stop the briefs asking for them
- [ ] **PR 7 — Un-blind the rule in the two files that still suppress it**: replace the blanket `// eslint-disable-next-line react-hooks/exhaustive-deps` in `src/theme/tokens.stories.tsx` and `src/theme/customCss.stories.tsx` with an explicit `set-state-in-effect` suppression, so the rule PR 3 installed can see into those functions again

  **The mechanism, because the file paths alone do not explain why this matters.** `exhaustive-deps` is one of the directives the React compiler reads as "the author knows they are breaking the rules of React", so it **bails on the entire enclosing function** and every compiler-backed rule goes quiet with it — `set-state-in-effect` included. The suppression is not local to the line it sits on. This is the same mechanism that made `CardConfig`'s `Modal` invisible in PR 4, where a deliberately blatant `setLocalConfig({})` in a bare `useEffect` reported nothing while the identical violation in a fresh component in the same file reported fine.

  **Verified in both directions** (PR 4, PR [#317](https://github.com/fx/liebe/pull/317)): removing only that comment from `CardConfig` made the `Modal`'s real effect **and** a planted one both report; adding such a comment to `useCameraStreamStatus.ts`, which was analysing correctly, silenced a planted violation there **and** turned that hook's own genuine `set-state-in-effect` suppression into an "unused eslint-disable directive" warning.

  **Neither effect here is a defect** — both are deliberate dependency-less effects reading computed styles off a live element, which genuinely cannot happen during render. What is wrong is that a future violation _beside_ them would land unreported, and the blind spot is **self-concealing**: the suppression that proves the rule once worked there afterwards reads as though it never needed to.

  **Scope limit, so the next reader does not over-generalise:** only `exhaustive-deps` was tested as a bail trigger. `set-state-in-effect`'s own suppression does **not** cause a bail — which is what makes the replacement a fix rather than a rename — and whether `rules-of-hooks` does is untested.

## Out of Scope

- **Making Storybook's a11y addon a contrast gate.** It cannot evaluate non-flat surfaces at all (incomplete ×31 under Liquid Glass), so it would be a gate with a silent hole. Contrast measurement belongs to [0035](./0035-light-appearance-contrast.md).
- **Speeding up the test suite.** Raising the timeout accepts that the assertions are slow; making them fast is separate work with no correctness consequence.
- **Rewriting the story matrices.** Whatever PR 6 decides, the existing stories keep their coverage; only their assertions' home is in question.
- **A general concurrency policy for the shared local stack.** `AGENTS.md` already handles it socially with an exclusive-slot rule; PR 2 removes the need for it, and codifying the social rule further is not worth doing twice.
