# 0040 — Test & CI Harness Reliability

## Summary

Five defects in the machinery that decides whether Liebe's code works, grouped because they share a failure mode rather than a subsystem: each produces a result that **looks like a pass and is not one**. The e2e harness runs one shared stack per machine whose bind mounts point at whichever worktree last brought it up, and it has already published a green 9/9 that executed entirely against another branch's bundle. Roughly two hundred Storybook `play` functions assert and nothing executes them — one of them has been wrong since it was written. Three test files flake under concurrent load and one leaks a timer past teardown, throwing an unhandled error while the suite reports green. And `react-hooks/set-state-in-effect` is configured as `error` but only matches bare `useEffect(...)`, so five `React.useEffect` member calls are invisible to it.

**Spec:** [architecture](../specs/architecture/index.md) → [testing & quality conventions](../specs/architecture/index.md#testing--quality-conventions), with the story-runner half in [storybook → CI & publishing](../specs/storybook/index.md#ci--publishing) · **Status:** draft · **Depends on:** —

Supersedes issues [#208](https://github.com/fx/liebe/issues/208), [#244](https://github.com/fx/liebe/issues/244), [#259](https://github.com/fx/liebe/issues/259), [#264](https://github.com/fx/liebe/issues/264), [#276](https://github.com/fx/liebe/issues/276).

## Motivation

`AGENTS.md` already states the principle these violate: _a probe that fails tells you something; a probe that passes tells you nothing until you have established it could have failed._ Every item here is a passing signal that could not have failed.

**The e2e harness.** `ha/docker-compose.yml` resolves to a single fixed project (`ha`, containers `liebe-e2e-ha` and `liebe-e2e-go2rtc`), so there is exactly one stack per machine and its bind mounts point at whichever worktree last ran `up`. Two checkouts running e2e concurrently silently serve each other's panel bundle and Home Assistant configuration. This is not hypothetical: worktree A built its bundle and ran its suite, worktree B recreated the containers against itself because it needed an `input_text` helper defined only in its own `configuration.yaml`, and A then re-ran the full suite and reported **9/9 passing** — every run executed against B's bundle and B's config. One of A's three new specs has still never run against A's own code. A's runs also mutated shared state on B's instance (`input_boolean.e2e_flag`), so B's results in that window are equally suspect and would have presented to B as unexplained flakiness in its own feature. The false pass was published in a pull request description before being caught. Neither side did anything unreasonable: the harness offers no way to tell whose stack you are talking to, and a contaminated run looks exactly like a clean one.

Separately, `npm run e2e:ha:up` cannot run as scripted — the invoking user is not in the `docker` group and a fresh workspace has no running daemon, so the documented path fails with a permission error on the socket. `AGENTS.md` now documents the `sudo service docker start` / `sg docker -c` workaround, which keeps people working and leaves the scripted path that the change documents point at still broken.

**Storybook `play` functions.** There is no story test-runner wired up, `*.stories.tsx` is excluded from coverage, Vitest collects `*.{test,spec}.*` only, and `build-storybook` proves compilation. The assertions read as tests to anyone reviewing a PR and were requested as tests in the coder briefs. The framing "an assertion that stopped asserting would be caught by nobody" turned out to understate it: the `Off` story in `MediaPlayerCard.stories.tsx` has been **wrong and failing since it was written**, asserting a `Turn on` pill against a fixture whose mask had bit 128 clear so no primary pill rendered. Verified by rendering that exact entity in a throwaway spec — red before the fixture fix, green after. That file's meta docblock states "Every story asserts rather than merely rendering", which is true of the code and false of the pipeline; its other ~19 play functions are unverified in both directions.

**The flakes.** Three files have flaked under concurrent load, none related to the diff being pushed: `ConfigurationMenu.test.tsx` with `window is not defined` after teardown, `WeatherCard.configSave.test.tsx` failing at 5987 ms, and `CardConfig` weather + `BinarySensorCard` config modal timing out at ~5 s under coverage instrumentation and passing with `--testTimeout=30000`. The duration evidence points at a class rather than three bugs: **tests with ~5 s implicit timeouts that only hold when the suite has the machine to itself** — the failing weather run took 50 s wall against 15 s for passing runs of the same commit, on a one-line markdown change. Coverage instrumentation pushes them over the same edge with no concurrency at all. `CardConfig.alarm.test.tsx` failed once on a documentation-only run and has never reproduced; whether it is a fourth instance of that class is an **untested hypothesis**, and it is recorded as one deliberately, because an issue saying "probably the same as #264" reads three weeks later as though someone checked.

`ConfigurationMenu`'s timer is a genuine bug rather than a timing sensitivity: a 3-second `setTimeout` outlives the test that scheduled it and throws after teardown regardless of how fast the machine is — as an unhandled error rather than a test failure, which is why the suite reports green while the process still fails. It failed a pre-push hook on a markdown-only diff, in the one place with no CI log to inspect afterwards.

**The lint rule.** `GridCard.tsx` writes `React.useEffect(...)`, which the rule does not match, and there is at least one real instance: `React.useEffect(() => { setDetailFor(null) }, [...])` — exactly the pattern the rule exists to reject. The cover card needed the same behaviour for change [0019](./0019-cover-fan-cards-to-spec.md), could not use the effect form because written as `useEffect(...)` the rule fires, and used the repo's lint-clean alternative instead. So the shell and the cards solve one problem two ways and the difference is not a decision anyone made: one of them was invisible to the linter. Five `React.useEffect` calls exist across `GridCard.tsx`, `ActionEditor.tsx` and `CardConfig.tsx`, and only one has been inspected.

## Requirements

### Testing Requirements

Per [architecture — Testing & Quality Conventions](../specs/architecture/index.md#testing--quality-conventions):

- `npm test`, `npm run lint`, `npm run typecheck` MUST pass; `codecov/patch` 100%; `codecov/project` no regress.
- **Every gate this change adds MUST be shown to fail.** A new gate that has only ever been observed green is the exact defect being fixed. Each PR MUST demonstrate its gate rejecting a deliberately broken input — a mismatched bundle, a wrong assertion, a `React.useEffect` writing state — and record that evidence.
- The bundle-identity check MUST be verified by an **actual mismatch**, not by reasoning: point the check at a stale bundle and show it throws with both hashes in the message.
- The story runner's first run MUST be treated as a discovery pass, not a pass/fail gate: roughly 200 previously-unexecuted assertions are expected to surface real failures. Each MUST be triaged as a wrong assertion or a real defect and recorded, and the PR MUST NOT delete a failing assertion to go green without saying which it was.
- Timeout changes MUST NOT be used to mask a leak. Raising `testTimeout` addresses the load-sensitivity class; the `ConfigurationMenu` timer MUST be fixed separately and MUST NOT be reported as fixed by a timeout change.

Skipping or weakening any rule to land the PR is a bug in the PR.

### Functional requirements

[architecture](../specs/architecture/index.md) owns the testing conventions, the coverage gates and the CI job set; [storybook](../specs/storybook/index.md) owns what stories are for — this change's acceptance criteria, not restated here. What implementing them requires of this change:

- **Both e2e fixes ship, and the identity check ships regardless.** Parameterising `COMPOSE_PROJECT_NAME` per checkout prevents the collision; the identity check makes any future collision **loud**. Fail-closed beats relying on discipline, and the check retains its value after the project name is parameterised.
- **The identity check MUST work over HTTP alone.** Asserting mount sources via `docker inspect` would be unavailable in exactly the environment where the contamination happened — the runner there cannot reach the docker socket without `sudo`. Hashing the served bundle and comparing against local `dist` needs no privileges and is conclusive on its own. Roughly 15–30 lines in `tests/e2e/global-setup.ts`, no new dependencies.
- **Hash the URL `configuration.yaml` actually points `module_url` at**, not a hardcoded `/local/dist/panel.js`. `tests/e2e/panel-loads.spec.ts` already parses that file for its own assertion, so the pattern exists; hardcoding the path would give the harness two sources of truth about where the bundle lives.
- **The skip MUST be an allowlist, not "anything that is not the mounted bundle".** Pointing e2e at the dev server on `:3000` is a legitimate workflow that would mismatch honestly, so that documented endpoint is exempt. Everything else **fails closed** — a stale path, a foreign host, or an unexpectedly remote bundle is also "not the mounted bundle", and skipping on that basis would re-admit the exact contamination this check exists to catch, silently and with a green tick. Both branches MUST be tested: the allowlisted dev-server URL skips, an unrecognised URL fails.
- **Ports follow the project name.** They are currently fixed too, so per-worktree stacks need per-worktree ports or they collide on bind instead of on mount.
- **The scripted startup MUST either work or fail loudly naming the cause.** A silent-ish permission error that people route around by hand is how a documented workflow rots. Detecting an unreachable daemon and exiting with a message that names it is acceptable; leaving the script to fail with a raw socket error is not.
- **The story-runner PR MUST also settle what stories are for.** If they stay documentation-grade, the coder briefs stop asking for "stories that assert" and the assertions move into the render-level tests that do run — roughly half duplicate a `__tests__` case already. If they become gate-grade, the storybook spec's CI section says so and the cost is accepted explicitly. Wiring a runner without settling this leaves ~200 slow assertions of undecided status in CI.
- **The lint fix and the cleanup are separable and MUST be sequenced.** Make the rule see member calls (or ban `React.useEffect` in favour of the imported form so the existing rule applies) first; then fix what it finds. Expect instances beyond the one inspected.
- **`AGENTS.md`'s e2e section MUST be reconciled** with whatever the scripts do afterwards. It currently documents a manual workaround as the working path; a fixed script makes that guidance wrong, and stale guidance about a gate is how the next contaminated run happens.

## Design Decisions

- **The hash check is preferred over asserting mount sources**, for a reason beyond taste: it works purely over HTTP and needs no docker privileges, so it is available in the environment where the contamination actually happened. A check built on `docker inspect` would be absent exactly there.
- **Both e2e fixes rather than either.** The project-name fix alone leaves the class silent if it recurs through some other route; the identity check alone leaves two worktrees fighting over one stack and merely tells them so. Together they make the collision impossible and any residual mismatch immediately fatal.
- **`CardConfig.alarm.test.tsx` is investigated, not assumed.** It is filed with no diagnosis on purpose — a guessed cause directs the next person's search. It MUST be checked for a timing-sensitive wait before being treated as an instance of the load-sensitivity class, and if no cause is found the honest outcome is to say so and leave it open rather than close it as "same as the others".
- **Raise `testTimeout` and fix the timer, as two things.** The instrumented run passing at 30 s is evidence that those assertions are correct and merely slow, which a timeout addresses. The `ConfigurationMenu` timer fires after teardown on any machine, which a timeout does not address and would hide. Conflating them would leave a real bug behind a config change.
- **The story-runner decision is a CI-semantics change, which is why it was never folded into a card PR.** It changes what a green CI run means for a dozen card families' worth of story matrices, and that is a decision to take deliberately with its cost stated.

## Out of Scope

- **Making Storybook's a11y addon a contrast gate.** It cannot evaluate non-flat surfaces at all (incomplete ×31 under Liquid Glass), so it would be a gate with a silent hole. Contrast measurement belongs to [0035](./0035-light-appearance-contrast.md).
- **Speeding up the test suite.** Raising the timeout accepts that the assertions are slow; making them fast is separate work with no correctness consequence.
- **Rewriting the story matrices.** Whatever PR 6 decides, the existing stories keep their coverage; only their assertions' home is in question.
- **A general concurrency policy for the shared local stack.** `AGENTS.md` already handles it socially with an exclusive-slot rule; PR 2 removes the need for it, and codifying the social rule further is not worth doing twice.
