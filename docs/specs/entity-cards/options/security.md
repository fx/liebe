# Card Options — Security (Lock & Alarm)

Extends the [common contract](./common.md); universal options (`name`, `icon`, `hideName`, `hideState`, `color`, `tapAction`, `holdAction`, `doubleTapAction`) apply as specified there and are not repeated here.

**Status: implemented** by change [0024](../../../changes/0024-security-cards.md). Both domains are registered, both accept the shared `CardProps` contract, and both render through the common shell with the standard loading / error / unavailable lifecycle states ([entity-cards — common shell](../index.md#common-card-shell-sizing-and-lifecycle-states)). Before this change both fell through to the fallback card, whose tap dispatched a toggle service neither domain registers — so on both of them the previous behaviour was an erroring tap rather than a control surface ([entity-cards — security](../index.md#security-lock-and-alarm)).

Security cards follow the [domain color discipline](../../design-system/index.md#domain-color-discipline) strictly: secure states (locked, armed) take `--liebe-c-ok` (green); insecure and emergency states (unlocked, triggered, jammed) take `--liebe-c-alert` (red). No other card family inverts "active = colored" this way — here the _safe_ state is the colored-calm one and the _unsafe_ state is the loud one.

## Lock card

Applies to entities in the `lock` domain. Entity states: `locked`, `unlocked`, `locking`, `unlocking`, `jammed`, and — on locks advertising the unlatch/`OPEN` feature — `opening` and `open` (plus `unavailable`/`unknown`, handled by the common shell).

### Primary action

`tapAction: default` for a lock card MUST mean **open more-info** (the entity detail dialog) — NOT toggle.

Rationale: locks are safety-critical. A toggle default makes a single accidental tap — a brushed sleeve on a wall tablet, a pocket touch — physically unlock a door. That failure mode is categorically worse than a light mis-toggle, so the domain default MUST NOT put unlock one ambient tap away. Locking and unlocking are instead explicit acts through dedicated buttons (`showButtons`, below), where unlock additionally carries a confirmation gate by default (`confirmUnlock`). Users who accept the risk MAY still set `tapAction: toggle` deliberately; the _default_ is what must be safe, per common convention 2 (defaults are the researched common case — and for locks the common case is "never unlock by accident"). A configured `toggle` resolves totally over lock states: `locked` → unlock (through `confirmUnlock`); `unlocked`/`open` → lock (through `confirmLock`); `locking`/`unlocking`/`opening` → inert (transition in progress; the pills' inverse-action rule governs explicit reversal); `jammed` → `more-info` (never guess a direction against a jammed mechanism); `unavailable`/`unknown` → inert.

- **GIVEN** a lock card with defaults
- **WHEN** the user taps the card body (not a Lock/Unlock button)
- **THEN** the entity detail dialog opens and no `lock.*` service is called.

### Options

All keys live under `item.config`, are camelCase, and follow the [common conventions](./common.md#conventions-for-per-card-options). Per convention 3, options only hide or tune what the entity supports.

| Key             | Type    | Default | Behavior                                                                                                                                                                                          |
| --------------- | ------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `showButtons`   | boolean | `true`  | Renders explicit **Lock** / **Unlock** pill buttons (`liebe-pill` anatomy). Tiers: `row`, `tall`, `full`. Never in `glance` (no room; glance stays more-info via tap).                            |
| `confirmUnlock` | boolean | `true`  | When `true`, activating Unlock (via button, or via a configured `toggle`/unlock action) MUST first show a confirmation dialog; `lock.unlock` is called only on confirm.                           |
| `confirmLock`   | boolean | `false` | Same gate for `lock.lock`. Off by default — locking is the safe direction and SHOULD stay one tap.                                                                                                |
| `doorEntity`    | string  | `''`    | Entity id of a linked `binary_sensor` (typically `device_class: door`). When non-empty and resolvable, the state line appends the door's open/closed reading. All tiers (subject to `hideState`). |

Prose notes:

- **`showButtons`.** The Unlock pill MUST render with alert-red accent and the Lock pill with ok-green accent, matching the state each button leads _away_ from. The pill for the current state (e.g. Lock while `locked`) MUST render disabled. **In `unavailable` and `unknown` both pills MUST render disabled and MUST NOT dispatch** — neither matches the current state, so a rule that only disables the matching pill would leave both live against a state the card cannot know, exactly where a lock command is least safe. This is the indeterminate-state rule, distinct from the transitional-state rule below: during `locking`/`unlocking` the inverse control deliberately stays enabled so the user can reverse the movement, but an indeterminate lock offers nothing to reverse. Buttons consume their own taps and MUST NOT trigger `tapAction` ([common contract — Action type](./common.md#action-type)). With `showButtons: false` the card is display-only unless the user configures explicit tap/hold actions.
- **`confirmUnlock` / `confirmLock`.** The confirmation dialog MUST name the entity ("Unlock _Front door_?") and MUST default focus to Cancel. Confirmation applies wherever the unlock (or lock) intent originates on this card — pills, `tapAction: toggle`, or a `call-service` action targeting `lock.unlock`/`lock.open` or any generic alias that resolves to this lock's unlock direction (`homeassistant.toggle`, `homeassistant.turn_on`/`turn_off` where the integration maps them — classification is by effect, per the common dispatch guarantees) — so the gate cannot be bypassed by re-routing the action; alias routes are covered by the confirmation tests. Two booleans rather than one because the directions are asymmetric: unlock is the dangerous direction, lock is the safe one. On a lock that demands a code, the keypad stands in for this dialog on the routes it covers — see [Code handling](#code-handling), which owns that rule and its one exception.
- **`doorEntity`.** Display-only linkage: the state line composes as `Locked · Door closed` (lock state colored per state, door fragment muted; an _open_ door fragment SHOULD take the alert text step, since "locked but open" deserves attention). An empty string (default), an unresolvable id, or an `unavailable` sensor MUST render the plain lock state with no fragment and no error. This option adds a reading from an entity the user already has — it never creates capability (convention 3).

### Code handling

Home Assistant's `lock.lock`, `lock.unlock` and `lock.open` all accept an optional `code`, and `LockEntity.state_attributes` publishes a `code_format` whenever an integration requires one. Keypad deadbolts are a common product category, so a lock card that could not carry a code would send commands such a lock refuses, with no card-level explanation — the failure arrives from the integration rather than from anything the card could see in advance.

**The keypad's own contract is the alarm's** — the [alarm card](#alarm-card)'s "Code handling (`showKeypad`)" prose note owns what it renders per `code_format`, that it masks input, that it sends the code with the call, and that it neither validates nor stores one. Those rules apply here unchanged and are deliberately not repeated; the same component collects for both domains. Three things differ, and each is a simplification rather than a second mechanism:

- **`code_format` alone decides it, in both directions.** A lock publishes no `code_arm_required` or any analogue, so a lock that publishes a format takes a code for locking exactly as it does for unlocking. The alarm's two-attribute rule — and the trap underneath it — has no counterpart here.
- **There is no `showKeypad` option.** The alarm's three-way option exists because a panel may want a keypad where no code is required (`always`) or none where one is (`never`); no such case has been demonstrated for a lock, and a lock's `code_format` answers the question on its own. A lock publishing a format always presents the keypad for a command this card dispatches; one publishing none never does, and behaves in every respect as it did before codes were specified — no keypad, no `code` field on the call, and the confirmation gates exactly where the table above puts them.
- **The keypad is always a dialog.** The alarm renders one inline on a `full` card of at least 2×3; the lock card is not given the effective span that floor is measured against, so it falls back to the dialog at every tier — the same omit-never-clip direction the alarm takes whenever its own span is unknown.

**The keypad replaces the confirmation; it is never stacked on top of one.** This is the alarm's rule and it carries its reason with it: the keypad _is_ the confirmation, entering a code being a strictly more deliberate act than answering "Unlock _Front door_?", and two prompts for one intent is how a confirmation becomes something people dismiss without reading. So a lock publishing a `code_format` MUST present the keypad **instead of** the `confirmUnlock` / `confirmLock` dialog for the pills and for a configured `tapAction: toggle`.

**A configured `call-service` route is the exception, and it stays gated.** Such a route is dispatched with the payload the user configured and no keypad of this card's stands in front of it, so no code of this card's can join it — which leaves the confirmation the only gate it meets, and suppressing that would leave a coded lock's re-routed unlock with nothing in front of it at all. `lock.open` reaches the device only by this path today: the card ships no unlatch control (see [Open Questions](#open-questions)), so there is nothing here to collect a code for, and the route is protected by classifying as an unlock direction. **When an unlatch control lands it takes a code the same way the other two do.**

**A refused code MUST be distinguishable from an accepted one.** The lock validates, so a wrong code comes back as a service error — and a keypad that closed on submit would make the two outcomes identical on screen, which on a credential surface is the one thing the user must be able to tell apart. So the keypad MUST stay open until the call settles: on success it closes, and on refusal it MUST report the failure next to the keypad and MUST allow another attempt (the entry is cleared and the at-most-once submit latch released). The alarm pins the same property from the other side, in its e2e spec "a wrong code is refused by the panel and changes nothing".

**The message MUST NOT contain the entered code.** What comes back is whatever the integration raised, and no card can enumerate what every integration puts in that string — so the code is stripped from the message before anything renders it, rather than the string being trusted. This is the only path by which a code could reach the DOM, and it applies wherever the message is surfaced, the card's own state line and `title` included.

- **GIVEN** a `locked` lock publishing `code_format: 'number'` with default options
- **WHEN** the user taps Unlock
- **THEN** a keypad is presented and no confirmation dialog is; **WHEN** the user enters a code and submits, **THEN** the card calls `lock.unlock` once, carrying that code, and the code is written nowhere else.

- **GIVEN** the same card with the keypad open
- **WHEN** the user submits a code the lock refuses
- **THEN** the keypad stays open, the refusal is reported beside it with the code stripped out of the message, and a second attempt can be entered and submitted.

### Tier layouts

Per [design-system — size-adaptive layouts](../../design-system/index.md#size-adaptive-layouts); content that does not fit MUST be omitted, never clipped.

| Tier           | Content                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `glance` (1×1) | Icon circle + name + state (with door fragment when configured). No buttons; whole tile is the primary action (more-info by default). |
| `row` (≥2×1)   | Icon + meta row, plus the Lock/Unlock pill pair (`showButtons`).                                                                      |
| `tall` (1×≥2)  | Icon on top, Lock/Unlock pills stacked vertically in the middle, meta at bottom.                                                      |
| `full` (≥2×≥2) | Row layout with full-width pills; the door sensor reading MAY expand to its own line with the sensor's friendly name.                 |

## Alarm card

Applies to entities in the `alarm_control_panel` domain. Entity states: `disarmed`, `armed_home`, `armed_away`, `armed_night`, `armed_vacation`, `armed_custom_bypass`, `arming`, `pending`, `disarming`, `triggered` — plus `unavailable`/`unknown`, where **every control (arm pills, Disarm, keypad) MUST render disabled and MUST NOT dispatch**, the same indeterminate-state rule the lock card follows: the common shell supplies the visual treatment but not control gating, and arming or disarming against a state the card cannot know is precisely the unsafe case. `disarming` (transitional) MUST render with the previous armed-state tint — or, when the card mounted mid-transition with no locally observed previous state, the generic armed green tint (disarming implies it was armed) — an in-progress spinner, and "Disarming…" muted state text; the Disarm control disables while its own disarm is in progress (nothing else to cancel — arm pills stay hidden as in every non-disarmed state), and the `row`/`tall` context pill shows Disarm disabled. Story coverage MUST include `disarming`. `unavailable`/`unknown` resolve with **highest priority**: the card renders the common shell's unavailable treatment, every control (pills, keypad, context pill) is disabled, and no `alarm_control_panel.*` service may dispatch from stale state — indeterminate never classifies as "non-disarmed"; both states in the story matrix.

### Primary action

`tapAction: default` for an alarm card MUST mean **open more-info**. The same safety reasoning as the lock applies, amplified: there is no sane "toggle" for an alarm panel (disarm ↔ which arm mode?), and disarming often requires a code — a bare tap can never carry that intent. For the same reason the alarm family MUST define the universal `toggle` action as resolving to `more-info` — an explicit family definition per the [common action type](./common.md#action-type), so a configured `tapAction: toggle` never falls back to `homeassistant.toggle` against an alarm panel. Arming and disarming happen through the explicit mode pills and the keypad flow below.

Prose notes:

#### When a code is required

Two attributes decide it, and **arming needs both of them**:

- **Disarming** requires a code exactly when the panel publishes a `code_format`.
- **Arming** requires a code exactly when the panel publishes a `code_format` **and** does not explicitly waive it via `code_arm_required: false`.

`code_arm_required` MUST NOT be read on its own, and the reason is that the obvious reading is wrong in the common case. Home Assistant defaults that attribute to **true** and publishes it on every panel whether or not one has a code — so a completely codeless panel reports `code_arm_required: true` alongside `code_format: null`. A card that consulted the flag alone would open a keypad on a panel that has no code to enter, and the panel would then refuse every arm attempt: **the card would make arming impossible**, with nothing on screen explaining why. `code_format` is what says a code _can_ be entered; `code_arm_required` only says whether arming _wants_ one.

An unreadable or absent `code_arm_required` leaves the panel's own default standing — only an explicit `false` waives the code. An unrecognised `code_format` (absent, `null`, or a value outside the formats Home Assistant defines) means no code format, and therefore no keypad; a panel that nonetheless wants one refuses the call, which surfaces through the standard error state.

- **`armModes`.** Default is _all supported_ modes, per convention 2 — zero configuration shows everything the panel can do; the option exists to hide modes a household never uses (e.g. hide `vacation` from a wall tablet). Selecting an arm pill MUST call the matching service (`alarm_control_panel.alarm_arm_home` / `alarm_arm_away` / `alarm_arm_night` / `alarm_arm_vacation`), passing the code when one was collected. The pill for the currently armed mode renders selected (green active tint); custom-bypass, when supported, is deferred to Open Questions.
- **Code handling (`showKeypad`).** When a code is required for a transition, initiating it MUST open a keypad: as a **dialog** in `glance`/`row`/`tall` tiers and in `full` cards below the size floor, and as an **inline keypad** within the card only when the `full` card's effective span is at least 2×3 (see the tier table — a 2×2 card cannot hold four ≥44px keypad rows without clipping). The keypad MUST honor the entity's `code_format` (`number` → digit pad, `text` → text field), MUST mask input, and MUST send the code with the arm/disarm service call — the card MUST NOT validate or store codes itself; validation is the panel's job and a rejected code surfaces as a service error. A code MUST never appear in the exported YAML.
- **`confirmDisarm`.** `true` by default, mirroring `confirmUnlock`: the keypad is the gate wherever one appears, so the default bites where nothing else stands between an accidental tap and `alarm_disarm`. Households that chose convenience set `false` deliberately.

- **The confirmation is suppressed by the KEYPAD, not by the code requirement.** The rule above is stated elsewhere in this document as "ignored when a code is required", and that phrasing is an imprecise expression of the reason behind it — the keypad **is** the confirmation, and an extra dialog would double-prompt. Where the two readings come apart, the reason governs: a transition that will present a keypad MUST NOT also raise a confirmation, and a transition that will not MUST still be gated by whichever of `confirmArm` / `confirmDisarm` applies. Two cases make it decidable, and the implementation follows both:
  - `showKeypad: always` on a **codeless** panel presents a keypad for a transition needing no code. No confirmation dialog may be stacked on top of it — two prompts for one intent is how a confirmation becomes something people dismiss without reading, which costs more than it protects.
  - `showKeypad: never` on a **code-protected** panel presents no keypad. The gate therefore still applies: suppressing the keypad MUST NOT also suppress the only remaining thing between a tap and `alarm_disarm`. The call is then made without a code, the panel refuses it, and that surfaces through the standard error state.

  This divergence between the literal wording and the implemented rule is recorded rather than silently carried, per the repo's rule that a spec and its code must not disagree unremarked.

#### `alarm_trigger` is deliberately not gated

The panic service actuates the panel, so the family's own rule — what cannot be proven harmless confirms — would put a confirmation in front of it. It is ungated anyway, and the reason is that **its failure mode is delay rather than accident**. A modal between someone in an emergency and the siren is itself the hazard. Every other gate on this card protects against an accidental _loss_ of security; gating this one would invert the property, trading a real emergency delay for protection against an outcome that is loud, obvious and immediately reversible.

Recorded because the obvious reading says otherwise: a reader who sees an actuating service pass ungated will take it for an oversight. It is not. A gate here needs an argument that beats the one above.

## Scenarios

### Scenario: Unlock is confirmation-gated by default

- **GIVEN** a `locked` lock card in `row` tier with default options (`confirmUnlock: true`)
- **WHEN** the user taps the Unlock pill and then Cancel in the confirmation dialog
- **THEN** no service is called and the lock stays `locked`; **WHEN** the user taps Unlock again and confirms, **THEN** the card calls `lock.unlock` and shows the `unlocking` spinner state until the entity reports `unlocked` (alert-red).

### Scenario: Jammed lock is unmissable

- **GIVEN** a lock card with `config: { color: 'ok', hideState: false }` whose entity transitions to `jammed`
- **WHEN** the card renders
- **THEN** the icon circle takes the alert tint and the state line reads "Jammed" in the alert text step — the `color` override does not apply to the jammed state.

### Scenario: Code-required arming opens the keypad dialog

- **GIVEN** a `disarmed` alarm card in `row` tier, entity with `code_arm_required: true` and `code_format: 'number'`, default options (`showKeypad: auto`)
- **WHEN** the user taps the "Arm away" pill, enters the code on the keypad dialog, and submits
- **THEN** the card calls `alarm_control_panel.alarm_arm_away` with the entered code, the dialog closes, and the card shows the amber `arming` pulse until the entity reports `armed_away` (green).

### Scenario: Disarm survives the exit countdown

- **GIVEN** an `arming` alarm card whose panel is counting down to `armed_away`
- **WHEN** the user looks for a way to stop it
- **THEN** the Disarm control is present and enabled, and stays so until the panel leaves the countdown — the transitional state disables only the control whose own command is in flight.

### Scenario: Triggered stays loud without motion

- **GIVEN** an alarm card with defaults (`flashOnTriggered: true`) on a device with `prefers-reduced-motion: reduce`, whose entity enters `triggered`
- **WHEN** the card renders
- **THEN** no flashing or pulsing occurs, but the card still shows the full-strength static alert treatment (alert tint, "TRIGGERED" state text) — the loud state survives with motion removed.

## Open Questions

- **`lock.open` (latch) support.** Locks advertising the open feature (unlatch) have a third, even more safety-critical action. Whether the card exposes an Open button (presumably behind its own confirmation) or leaves unlatching to more-info is still undecided; **as implemented there is no built-in unlatch control**, so `opening` and `open` are rendered as states only. The gate half is settled and shipped: `confirmUnlock` covers the entire unlock direction at action resolution, and a configured `call-service` targeting `lock.open` passes the same confirmation as `lock.unlock`, so the deferred control cannot be reached ungated by re-routing. Because no control consults the unlatch feature bit, the card reads no lock feature bits at all — a reader is one is not missing.
- **Custom bypass arm mode.** `armed_custom_bypass` is a valid state and arm service but is intentionally absent from `armModes` (rare, installer-specific). Whether to add it to the multi-select when the entity supports it is open. As implemented, capability is necessary but not sufficient: a panel advertising the custom-bypass feature is still not offered the mode, because the choices are narrowed from the modes this document lists rather than built up from the panel's bits. The state itself renders normally when a panel reaches it by other means.
- **Door sensor auto-discovery.** `doorEntity` is manual. HA device registries could suggest a same-device `binary_sensor` as the default; whether the config editor should pre-fill it is open.
- **Triggered attention beyond the card.** A triggered alarm arguably warrants dashboard-level attention (screen-edge glow, notification), not just card styling; that would belong to a separate spec, not this option surface.
- **Keypad in `tall` tier.** `tall` (1 wide) uses the dialog keypad as specified; whether a narrow inline keypad is feasible at 1-cell width remains open. As implemented the inline keypad appears only on a `full` card of at least 2×3 and every other case falls back to the dialog, including a `full` card below that floor and one whose span is not known.
