# Card Options — Security (Lock & Alarm)

Extends the [common contract](./common.md); universal options (`name`, `icon`, `hideName`, `hideState`, `color`, `tapAction`, `holdAction`, `doubleTapAction`) apply as specified there and are not repeated here.

**Status: specified, not yet implemented (new cards).** Neither the `lock` nor the `alarm_control_panel` domain has a card today — both currently fall back to `ButtonCard` via the registry ([entity-cards — registry](../index.md#card-dispatch-and-registry)). This document specifies the option surface for the two new cards. Both MUST be registered in `domainToCard` (`lock` → LockCard, `alarm_control_panel` → AlarmCard), MUST accept the shared `CardProps` contract, and MUST render through the common shell with the standard loading / error / unavailable lifecycle states ([entity-cards — common shell](../index.md#common-card-shell-sizing-and-lifecycle-states)).

Security cards follow the [domain color discipline](../../design-system/#domain-color-discipline) strictly: secure states (locked, armed) take `--liebe-c-ok` (green); insecure and emergency states (unlocked, triggered, jammed) take `--liebe-c-alert` (red). No other card family inverts "active = colored" this way — here the _safe_ state is the colored-calm one and the _unsafe_ state is the loud one.

## Lock card

Applies to entities in the `lock` domain. Entity states: `locked`, `unlocked`, `locking`, `unlocking`, `jammed`, and — on locks advertising the unlatch/`OPEN` feature — `opening` and `open` (plus `unavailable`/`unknown`, handled by the common shell).

### Primary action

`tapAction: default` for a lock card MUST mean **open more-info** (the entity detail dialog) — NOT toggle.

Rationale: locks are safety-critical. A toggle default makes a single accidental tap — a brushed sleeve on a wall tablet, a pocket touch — physically unlock a door. That failure mode is categorically worse than a light mis-toggle, so the domain default MUST NOT put unlock one ambient tap away. Locking and unlocking are instead explicit acts through dedicated buttons (`showButtons`, below), where unlock additionally carries a confirmation gate by default (`confirmUnlock`). Users who accept the risk MAY still set `tapAction: toggle` deliberately; the _default_ is what must be safe, per common convention 2 (defaults are the researched common case — and for locks the common case is "never unlock by accident"). A configured `toggle` resolves totally over lock states: `locked` → unlock (through `confirmUnlock`); `unlocked`/`open` → lock (through `confirmLock`); `locking`/`unlocking`/`opening` → inert (transition in progress; the pills' inverse-action rule governs explicit reversal); `jammed` → `more-info` (never guess a direction against a jammed mechanism); `unavailable`/`unknown` → inert.

- **GIVEN** a lock card with defaults
- **WHEN** the user taps the card body (not a Lock/Unlock button)
- **THEN** the entity detail dialog opens and no `lock.*` service is called.

### Options

All keys live under `item.config`, are camelCase, and follow the [common conventions](./common.md#conventions-for-per-card-options). Per convention 3, options only hide or tune what the entity supports.

| Key             | Type    | Default | Behavior                                                                                                                                                                                          |
| --------------- | ------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `showButtons`   | boolean | `true`  | Renders explicit **Lock** / **Unlock** pill buttons (`liebe-pill` anatomy). Tiers: `row`, `tall`, `full`. Never in `glance` (no room; glance stays more-info via tap).                            |
| `confirmUnlock` | boolean | `true`  | When `true`, activating Unlock (via button, or via a configured `toggle`/unlock action) MUST first show a confirmation dialog; `lock.unlock` is called only on confirm.                           |
| `confirmLock`   | boolean | `false` | Same gate for `lock.lock`. Off by default — locking is the safe direction and SHOULD stay one tap.                                                                                                |
| `doorEntity`    | string  | `''`    | Entity id of a linked `binary_sensor` (typically `device_class: door`). When non-empty and resolvable, the state line appends the door's open/closed reading. All tiers (subject to `hideState`). |

Prose notes:

- **`showButtons`.** The Unlock pill MUST render with alert-red accent and the Lock pill with ok-green accent, matching the state each button leads _away_ from. The pill for the current state (e.g. Lock while `locked`) MUST render disabled. Buttons consume their own taps and MUST NOT trigger `tapAction` ([common contract — Action type](./common.md#action-type)). With `showButtons: false` the card is display-only unless the user configures explicit tap/hold actions.
- **`confirmUnlock` / `confirmLock`.** The confirmation dialog MUST name the entity ("Unlock _Front door_?") and MUST default focus to Cancel. Confirmation applies wherever the unlock (or lock) intent originates on this card — pills, `tapAction: toggle`, or a `call-service` action targeting `lock.unlock`/`lock.open` or any generic alias that resolves to this lock's unlock direction (`homeassistant.toggle`, `homeassistant.turn_on`/`turn_off` where the integration maps them — classification is by effect, per the common dispatch guarantees) — so the gate cannot be bypassed by re-routing the action; alias routes are covered by the confirmation tests. Two booleans rather than one because the directions are asymmetric: unlock is the dangerous direction, lock is the safe one.
- **`doorEntity`.** Display-only linkage: the state line composes as `Locked · Door closed` (lock state colored per state, door fragment muted; an _open_ door fragment SHOULD take the alert text step, since "locked but open" deserves attention). An empty string (default), an unresolvable id, or an `unavailable` sensor MUST render the plain lock state with no fragment and no error. This option adds a reading from an entity the user already has — it never creates capability (convention 3).

### States

State rendering MUST follow the [active-tint pattern](../../design-system/#domain-color-discipline):

| Entity state            | Icon circle                                                                                                                                                                                                                                                     | State text                                    | Notes                                                                                                                                                                                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `locked`                | Green tint (`--liebe-c-ok`), closed-padlock glyph                                                                                                                                                                                                               | "Locked", green text step                     |                                                                                                                                                                                                                                                                                                                  |
| `unlocked`              | Alert tint (`--liebe-c-alert`), open-padlock glyph                                                                                                                                                                                                              | "Unlocked", alert text step                   | Red-as-unlocked is the domain discipline: insecure is loud.                                                                                                                                                                                                                                                      |
| `locking` / `unlocking` | Previous-state tint — inferred from the transition's direction when no locally observed previous state exists (a card mounting mid-transition has none): `locking` implies previous `unlocked` (alert tint), `unlocking` implies previous `locked` (green tint) | "Locking…" / "Unlocking…", muted              | Only the button for the in-progress direction disables; the **inverse button stays enabled** so an unwanted transition can be reversed (its confirm gate still applies).                                                                                                                                         |
| `opening`               | Same transitional treatment as `unlocking`                                                                                                                                                                                                                      | "Opening…", muted                             | Transitional (unlatch in progress); Unlock disables (already past it), **Lock stays enabled** to re-secure.                                                                                                                                                                                                      |
| `open`                  | Alert tint, open-door glyph                                                                                                                                                                                                                                     | "Open" in the alert text step                 | Door unlatched: Lock enabled, Unlock disabled (already past unlocked). A dedicated unlatch (`lock.open`) control is deliberately NOT part of this option surface — deferred until demand is demonstrated; these states exist so unlatch-capable locks always render defined labels, colors, and button behavior. |
| `jammed`                | Alert tint, jam/warning glyph                                                                                                                                                                                                                                   | MUST read **"Jammed"** in the alert text step | MUST use alert color and an explicit label — a jammed lock is a physical-security failure and MUST NOT be renderable as anything calmer, regardless of `color` override or options.                                                                                                                              |

### Tier layouts

Per [design-system — size-adaptive layouts](../../design-system/#size-adaptive-layouts); content that does not fit MUST be omitted, never clipped.

| Tier           | Content                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `glance` (1×1) | Icon circle + name + state (with door fragment when configured). No buttons; whole tile is the primary action (more-info by default). |
| `row` (≥2×1)   | Icon + meta row, plus the Lock/Unlock pill pair (`showButtons`).                                                                      |
| `tall` (1×≥2)  | Icon on top, Lock/Unlock pills stacked vertically in the middle, meta at bottom.                                                      |
| `full` (≥2×≥2) | Row layout with full-width pills; the door sensor reading MAY expand to its own line with the sensor's friendly name.                 |

## Alarm card

Applies to entities in the `alarm_control_panel` domain. Entity states: `disarmed`, `armed_home`, `armed_away`, `armed_night`, `armed_vacation`, `armed_custom_bypass`, `arming`, `pending`, `disarming`, `triggered`. `disarming` (transitional) MUST render with the previous armed-state tint — or, when the card mounted mid-transition with no locally observed previous state, the generic armed green tint (disarming implies it was armed) — an in-progress spinner, and "Disarming…" muted state text; the Disarm control disables while its own disarm is in progress (nothing else to cancel — arm pills stay hidden as in every non-disarmed state), and the `row`/`tall` context pill shows Disarm disabled. Story coverage MUST include `disarming`. `unavailable`/`unknown` resolve with **highest priority**: the card renders the common shell's unavailable treatment, every control (pills, keypad, context pill) is disabled, and no `alarm_control_panel.*` service may dispatch from stale state — indeterminate never classifies as "non-disarmed"; both states in the story matrix.

### Primary action

`tapAction: default` for an alarm card MUST mean **open more-info**. The same safety reasoning as the lock applies, amplified: there is no sane "toggle" for an alarm panel (disarm ↔ which arm mode?), and disarming often requires a code — a bare tap can never carry that intent. For the same reason the alarm family MUST define the universal `toggle` action as resolving to `more-info` — an explicit family definition per the [common action type](./common.md#action-type), so a configured `tapAction: toggle` never falls back to `homeassistant.toggle` against an alarm panel. Arming and disarming happen through the explicit mode pills and the keypad flow below.

### Options

| Key                | Type                                                              | Default                                              | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------ | ----------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `armModes`         | ordered multi-select of `home` \| `away` \| `night` \| `vacation` | all supported (order: `away, home, night, vacation`) | Which arm modes render as pills, **in list order** — the first entry is also the `row`/`tall` single-pill mode. The choice set MUST be derived from the entity's `supported_features` (arm-home, arm-away, arm-night, arm-vacation bits); the config editor MUST offer only supported modes, and stored modes the entity does not support MUST be ignored at render time. The full pill row renders in the `full` tier; `row`/`tall` render the single context pill (first listed mode when disarmed, Disarm otherwise — see Tier layouts); `glance` surfaces arming via more-info.                                                                   |
| `showKeypad`       | select: `auto` \| `always` \| `never`                             | `auto`                                               | `auto` shows a keypad exactly when the entity requires a code for the attempted transition (`code_arm_required` for arming; disarm per `code_format`). `always` shows it for every arm/disarm even when no code is needed (code sent only if entered); when the panel exposes no `code_format` (the normal codeless case), the keypad defaults to the **digit pad** (`number` presentation) — the overwhelmingly common alarm-code shape — deterministically, and an entered code is still sent with the call. `never` suppresses it — transitions the entity refuses without a code will surface the service error through the standard error state. |
| `confirmArm`       | boolean                                                           | `false`                                              | When `true` and no code is required for arming (`code_arm_required: false`), arm actions — pills and same-entity `call-service` `alarm_arm_*` routes alike, applied at action resolution — show a confirmation dialog first. Deliberately off by default: the safety asymmetry is real — a mistaken **arm** is an inconvenience reversed by the (gated or coded) disarm, while a mistaken **disarm** is a security breach — and one-tap arming is the ecosystem norm. Households wanting symmetry opt in.                                                                                                                                             |
| `confirmDisarm`    | boolean                                                           | `true`                                               | When **no code is required**, disarming MUST show a confirmation dialog first — on by default, because a codeless panel otherwise puts `alarm_disarm` one accidental tap away with no gate at all (the same reasoning as `confirmUnlock`; users accepting the risk set `false` deliberately). When a code is required this option is irrelevant and MUST be ignored — the keypad _is_ the confirmation (an extra dialog would double-prompt).                                                                                                                                                                                                         |
| `flashOnTriggered` | boolean                                                           | `true`                                               | When `triggered`, the card pulses its alert background (see [States](#states-and-colors)). MUST be disabled automatically under `prefers-reduced-motion: reduce` regardless of this setting.                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

Prose notes:

- **`armModes`.** Default is _all supported_ modes, per convention 2 — zero configuration shows everything the panel can do; the option exists to hide modes a household never uses (e.g. hide `vacation` from a wall tablet). Selecting an arm pill MUST call the matching service (`alarm_control_panel.alarm_arm_home` / `alarm_arm_away` / `alarm_arm_night` / `alarm_arm_vacation`), passing the code when one was collected. The pill for the currently armed mode renders selected (green active tint); custom-bypass, when supported, is deferred to Open Questions.
- **Code handling (`showKeypad`).** When a code is required for a transition, initiating it MUST open a keypad: as a **dialog** in `glance`/`row`/`tall` tiers and in `full` cards below the size floor, and as an **inline keypad** within the card only when the `full` card's effective span is at least 2×3 (see the tier table — a 2×2 card cannot hold four ≥44px keypad rows without clipping). The keypad MUST honor the entity's `code_format` (`number` → digit pad, `text` → text field), MUST mask input, and MUST send the code with the arm/disarm service call — the card MUST NOT validate or store codes itself; validation is the panel's job and a rejected code surfaces as a service error. A code MUST never appear in the exported YAML.
- **`confirmDisarm`.** `true` by default, mirroring `confirmUnlock`: on a code-protected panel the option is inert (the keypad is the gate), so the default only bites on **codeless** panels — exactly where nothing else stands between an accidental tap and `alarm_disarm`. Codeless households that chose convenience set `false` deliberately.

### States and colors

| Entity state         | Rendering                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `disarmed`           | Neutral: muted glyph on the inactive neutral circle, state text muted. Disarmed is a chosen idle state, not an alert.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `armed_*`            | Green (`--liebe-c-ok`) active tint; state text names the mode ("Armed away") in the green text step.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `arming` / `pending` | Amber active tint (`--liebe-c-light` scale) with a **pulse** on the icon circle — the exit/entry-delay countdown is the one moment the user must notice in time. Pulse suppressed under `prefers-reduced-motion` (a static amber state remains).                                                                                                                                                                                                                                                                                                                                                     |
| `triggered`          | Alert red, and MUST be **visually loud**: alert active tint at full strength, state text "TRIGGERED" in the alert step, and — with `flashOnTriggered: true` — a pulsing alert-tint card background. A triggered card MUST remain unambiguous with all motion disabled (static full-strength alert treatment); motion is emphasis, never the sole signal. **Neither `hideState` nor `color` can soften it**: the alert treatment overrides any named `color`, exactly as the `jammed` lock state does. A triggered alarm rendered calm green would be the single worst failure this card can produce. |

### Tier layouts

| Tier           | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `glance` (1×1) | Icon circle + name + state. Tap opens more-info; arm/disarm happens there (with keypad dialog when required).                                                                                                                                                                                                                                                                                                                                                                           |
| `row` (≥2×1)   | Icon + meta row, plus a single context action pill: **Disarm** when armed/**arming**/pending/triggered (every non-disarmed state — Disarm stays reachable through the exit countdown, per the Disarm rules), or — when disarmed — the **first mode in the configured `armModes` list** (list order is user-editable; default order `away, home, night, vacation`), a deterministic choice since Home Assistant exposes no "primary arm mode". Keypad appears as a dialog when required. |
| `tall` (1×≥2)  | Icon on top, the context action pill mid-card, meta at bottom.                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `full` (≥2×≥2) | Row layout plus the **arm-mode pill row** (`armModes`) and **Disarm**. The keypad renders inline only when the **effective span is at least 2×3** — four keypad rows of ≥44px targets cannot coexist with the row layout, pills, and padding inside a 2×2 card without violating the no-clipping contract; below that floor (including minimum `full` at 2×2), code entry stays a dialog even with `showKeypad: always`.                                                                |

## Scenarios

### Scenario: Unlock is confirmation-gated by default

- **GIVEN** a `locked` lock card in `row` tier with default options (`confirmUnlock: true`)
- **WHEN** the user taps the Unlock pill and then Cancel in the confirmation dialog
- **THEN** no service is called and the lock stays `locked`; **WHEN** the user taps Unlock again and confirms, **THEN** the card calls `lock.unlock` and shows the `unlocking` spinner state until the entity reports `unlocked` (alert-red).

### Scenario: Jammed lock is unmissable

- **GIVEN** a lock card with `config: { color: 'ok', hideState: false }` whose entity transitions to `jammed`
- **WHEN** the card renders
- **THEN** the icon circle takes the alert tint and the state line reads "Jammed" in the alert text step — the `color` override does not apply to the jammed state.

### Scenario: Code-required arming opens the keypad dialog

- **GIVEN** a `disarmed` alarm card in `row` tier, entity with `code_arm_required: true` and `code_format: 'number'`, default options (`showKeypad: auto`)
- **WHEN** the user taps the "Arm away" pill, enters the code on the keypad dialog, and submits
- **THEN** the card calls `alarm_control_panel.alarm_arm_away` with the entered code, the dialog closes, and the card shows the amber `arming` pulse until the entity reports `armed_away` (green).

### Scenario: Triggered stays loud without motion

- **GIVEN** an alarm card with defaults (`flashOnTriggered: true`) on a device with `prefers-reduced-motion: reduce`, whose entity enters `triggered`
- **WHEN** the card renders
- **THEN** no flashing or pulsing occurs, but the card still shows the full-strength static alert treatment (alert tint, "TRIGGERED" state text) — the loud state survives with motion removed.

## Open Questions

- **`lock.open` (latch) support.** Locks advertising the open feature (unlatch) have a third, even more safety-critical action. Whether the card exposes an Open button (presumably behind its own confirmation) or leaves unlatching to more-info is undecided. **Decided regardless of that question:** the `confirmUnlock` gate covers the entire unlock direction at action resolution — a configured `call-service` targeting `lock.open` MUST pass the same confirmation as `lock.unlock`, so the deferred built-in control cannot be bypassed by re-routing.
- **Custom bypass arm mode.** `armed_custom_bypass` is a valid state and arm service but is intentionally absent from `armModes` (rare, installer-specific). Whether to add it to the multi-select when the entity supports it is open.
- **Door sensor auto-discovery.** `doorEntity` is manual. HA device registries could suggest a same-device `binary_sensor` as the default; whether the config editor should pre-fill it is open.
- **Triggered attention beyond the card.** A triggered alarm arguably warrants dashboard-level attention (screen-edge glow, notification), not just card styling; that would belong to a separate spec, not this option surface.
- **Keypad in `tall` tier.** `tall` (1 wide) is specified to use the dialog keypad; whether a narrow inline keypad is feasible at 1-cell width is deferred until the tier system is implemented.
